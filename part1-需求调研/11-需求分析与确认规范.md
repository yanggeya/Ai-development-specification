# 11-需求分析与确认规范 —— 从问答到冻结的需求

> **本文件规定调研问答完成后，如何把零散信息整理成可确认、可冻结、可追溯的需求。**

- 版本：v1.7
- 前置阅读：`10-需求调研规范.md`
- 参考底稿：`13-需求工程参考与方法论.md`（业界框架对照，可选）

---

## 一、分析步骤

### 1. 功能边界划分（做什么 / 不做什么）

对每个候选功能点做三档判定：

| 判定 | 含义 | 处理 |
|------|------|------|
| **做** | 本期范围内 | 写入 T2 功能清单，分配功能编号 |
| **不做** | 明确排除 | 写入 T1「范围外事项」，说明原因（防止后期扯皮和范围蔓延） |
| **待定** | 拿不准 | 写入 T1「开放问题」，给出建议，请用户决策 |

### 2. 优先级评定（功能优先级）

| 功能优先级 | 定义 | 判断标准 |
|--------|------|---------|
| **必需** | 必须 | 没有它主流程跑不通 |
| **重要** | 核心价值但可二期 | |
| **增强** | 锦上添花 | |

> 注：此处「功能优先级（必需/重要/增强）」是**需求维度**，与总则「任务分级 P1/P2/P3（重大/一般/小改动）」是**两个不同维度**，不要因字母 P 混淆。某个需求功能可以是「必需」但工作量只是 P2（小改），也可以是「增强」但工作量 P1（大改）。

### 3. 验收标准制定（每个功能点必须可验证）

验收标准必须满足：**给出输入和操作，能明确判断结果对不对**。

- ✅ 好的标准："用户输入不存在的资产名搜索，列表显示空并提示'无匹配结果'，耗时 < 1 秒"
- ❌ 差的标准："搜索功能好用"

### 4. 依赖与风险标注

- 功能点之间的依赖关系（谁先做）；
- 技术上拿不准的点（需要预研的）；
- 依赖外部条件的（第三方接口、客户提供的数据）。

## 二、需求冻结机制

1. T1（需求文档）与 T2（功能清单）完成后，提交用户逐项确认；
2. 用户确认后文档标记状态为**「已确认」**，即视为**需求冻结**；
3. 冻结后任何需求变化（新增、修改、删除功能点）必须走《30-变更控制规范》，不允许口头直接改；
4. 冻结的意义：后续所有开发、测试、验收都以冻结版文档为唯一依据。

> **需求是活文档，演进是常态而非异常。** 冻结只是"一轮基线确认"，开发过程中的调整——开发者试做后发现需求要改、用户中途追加或删减功能——是正常且频繁的，不得视为"偏离"。演进时仍须走《30-变更控制规范》，但**落点不是"追加一条修订记录"**，而是：
> - 改 **T1 / T2 正文**——第 3 节功能描述、第 2 节角色、第 5 节技术约束、第 6 节范围外、第 7 节开放问题等，直接改写为**当前完整需求**；
> - T1 / T2 读起来始终是"当前完整需求"，而不是"原始需求 + 一堆修订"；
> - CHANGELOG / T1 顶部「变更记录」只记"变了什么、为什么"（追溯用），**不承载需求本身**。
> 一句话：**CHANGELOG 记"变了什么"，T1/T2 正文记"现在要做什么"。**

## 三、产出物要求

| 产出物 | 使用模板 | 质量门槛 |
|--------|---------|---------|
| T1 项目需求文档 | `templates/T1-项目需求文档模板.md` | 检查清单（见《10》第三节）全部通过 |
| T2 功能清单 | `templates/T2-功能清单模板.md` | 每个功能点有唯一编号、优先级、功能要求摘要、核心验收点（可验证），且通过「全局功能覆盖自检」 |
| 开放问题清单（附在 T1 内） | — | 每项有建议方案，等待用户决策 |

> 生成以上产出物时，可参考《13-需求工程参考与方法论》对齐业界通行框架（如 Kano 优先级、INVEST 验收标准、Google PRD 结构），但**不得因此增加用户阅读负担**。

## 四、确认话术（提交用户时使用）

提交确认时，AI 必须按此结构呈现，便于用户快速审阅：

```
已完成需求整理，请确认以下要点：
1. 业务目标：<一句话>
2. 本期功能（必需）：<功能点列表，每条一句话>
3. 重要功能（可选做/增强）：<列表或"无">
4. 明确不做的：<列表，请特别注意>
5. 前期技术约束确认（数据库选型/技术栈/部署环境/外部依赖/安全合规级别/数据迁移/国际化/运维/认证体系/多租户隔离/API 风格/成本预算/UI 风格与前端规范（含设计稿来源））：<已确认项 + 待定项>
6. 待您决策的开放问题：<列表 + 建议>
确认无误后我将冻结需求进入设计阶段；任何调整请直接指出。
```

## 五、需求确认后：告知开发流程 + 建立开发计划表（必做）

需求冻结（T1/T2 标记「已确认」）后，**AI 不能闷头进设计写码**，必须先做两件事：

### 1. 主动告知用户后续开发流程

用一句话 + 一张阶段表，让用户清楚"接下来会经历什么、每个阶段产出什么、卡在哪道门"：

```
需求已冻结，进入开发。后续流程（每阶段有产出文档与出门标准）：
  ① 设计  → T3/T4/T5（涉及模块才做）
  ② 编码  → 按文档写码 + 每功能一份 T8 功能说明
  ③ 测试  → T6 测试记录，逐条回溯验收标准
  ④ 安全  → T10 安全测试报告（无未处置严重/高危漏洞才放行）
  ⑤ 上线  → T7 上线方案（无回滚方案不上线、无 T10 不上线）
  ⑥ 部署  → 按 T11 部署文档执行，回写 CHANGELOG
任何阶段要改需求，走《30-变更控制规范》。现在我先建《开发计划表》把功能排期。
```

### 2. 建立开发计划表

按模板 `part2-开发/templates/T-开发计划表模板.md` 在 `docs/开发计划表.md` 建立计划，把 T2 功能清单映射为开发任务（阶段 / 优先级 / 依赖 / 负责 / 估算 / 状态 / 关联文档）。它是开发排期基线：

- **不是一次性文档**：开发推进中持续更新任务状态；
- **需求变更要同步回表**：走《30-变更控制规范》的变更，必须同步更新本表对应任务并关联 CHANGELOG。

> 缺《开发计划表》直接进编码 = 无排期无跟踪，视为需求阶段未完成。接手项目在《12》第 5 步确认后同样适用本节的"告知流程 + 建计划表"。
