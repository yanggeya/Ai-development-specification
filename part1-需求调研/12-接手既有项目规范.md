# 12-接手既有项目规范 —— 半路接手怎么干

> **本文件规定 AI 接手一个已经开发到一半、文档不全或没有文档的项目时，如何盘点现状、反向梳理需求、补建文档，把它纳入本规范体系后再继续开发。**
>
> 核心思想：**先搞清楚"现在有什么"，再谈"要做什么"——禁止在没摸清现状的情况下贸然改代码。**

- 版本：v1.8
- 前置阅读：`00-总则.md`

---

## 一、接手总原则

1. **先读后写**：接手第一步永远是"读"——读代码、读配置、读已有文档、读数据库结构，不是急着改东西；
2. **文档反向补建**：既有项目缺什么文档补什么文档，直到达到本体系的基础门槛（至少有 **T1 项目需求 + T2 功能清单 + T9 功能树 + 每功能一份 T8**），才进入正常开发流程；
3. **现状即基线**：补建的文档是对"代码现状"的客观描述，不是对"理想设计"的描写——描述现状用陈述句，发现的疑点标记为【待确认】单独列出，不擅自下结论；
4. **改动延后**：盘点期间不修改任何代码，发现的 Bug/待优化点只记录成清单，交用户决定优先级，不顺手改。
5. **代码为真相源（Code as Source of Truth）**：文档、README、用户口述、目录名、函数命名都可能与实际实现不一致——文档常过时、README 常只写理想状态、注释常失效、命名常误导。对"功能作用 / 行为逻辑 / 接口契约 / 数据结构"的任何结论，**必须回到实际源码逐行核对验证**，不得仅凭文档或命名推断下结论。
6. **问题找对人（优先问开发人）**：盘点中遇到的待确认问题，优先向**原开发人**核实——过渡期他能提供文档/口述没有的实现背景与历史决策；原开发人已无法联系或不清楚的，再交用户拍板，**禁止凭空臆测**。
7. **文档落地为文件**：接手产出的所有文档（T1/T2/T8/T9/T4/T5/T3/T11）必须**实际创建为项目 `docs/` 目录下的文件**（含建立目录骨架），不能只停在对话里或写成计划清单；首次接手先搭好 `docs/` 目录结构，再逐项填内容。
8. **冲突须问用户定夺，且必须落文档、有解决记录**：盘点中发现实际代码与已有文档（需求/设计/README）出现实质不一致时，**不能默默以任一方覆盖另一方**。所有冲突必须登记进独立文档 `docs/接手冲突核对与解决记录.md`（按模板 `T-接手冲突核对模板.md`），**不得只停留在对话或报告里**。该文档每条冲突含两部分：①**冲突登记**——写清"文档说 A、代码实际做 B"、冲突类型（需求/接口/数据结构/行为逻辑等）；②**解决记录**——写清裁定结论（以代码为准 / 以文档为准）、裁定人、裁定日期、处置动作与关联文件。裁定前保持中立，不擅自下结论；用户裁定后：以代码为准 → 文档按代码修订并标注【代码与文档不一致，用户确认以代码为准】；以文档为准 → 代码视为偏离/待修复，记入待修复清单（不动代码，见原则 4）。缺"冲突登记"或"解决记录"任一，视为接手未完成。
9. **接手后修改仍须同步 T8，且冲突记录长期有效**：接手完成、进入正常流程后，任何功能修改都须遵守《30-变更控制规范》的 T8 同步门禁——反向补建的 T8 即功能唯一事实源，必须随代码同步更新（不是"临时文档"）。`docs/接手冲突核对与解决记录.md` 是长期有效的项目档案，后续若改动涉及某条已解决冲突对应的功能 / 代码，须在原条目追加"后续变更"备注（日期 / 变更摘要 / 是否推翻原裁定），不得丢弃或覆盖。

## 二、接手工作流（五步）

### 第 1 步：信息收集（能拿到的都看一遍）

按下列顺序收集，缺的标记"无"：

| 信息源 | 看什么 | 产出 |
|--------|--------|------|
| 已有文档 | 需求文档、设计文档、README、wiki | 文档清单（有的列出，没有的标注） |
| 代码仓库 | 目录结构、**实际通读入口文件与核心业务模块代码**、技术栈、依赖清单、配置加载与错误处理实现 | 现状架构说明（须来自实际代码，不止目录） |
| 数据库 | 表清单、字段、索引、枚举值 | 现状库表清单 |
| 接口 | 已有 API 列表、请求响应结构 | 现状接口清单 |
| 配置 | 环境变量、部署配置、定时任务 | 运行环境说明 |
| 运行状态 | 是否能跑起来、核心流程能否走通 | 可运行性结论 |
| **部署现状** | 部署在哪（服务器/容器/平台）、有几个环境（dev/test/prod）、域名与端口、依赖中间件、数据库备份情况、是否有部署文档 | 部署现状说明（有文档则收集，无则备注"无文档，待补建 T11"） |

**如果项目能运行**：实际操作一遍主流程，记录"用户做什么→系统响应什么"，比纯看代码更准。

**⚠️ 代码实地检查（核心要求）**：即使项目有文档/README，也要**抽样实际读代码**核对——文档常过时、README 常只写理想状态、注释常失效。重点看：
1. 程序入口与启动逻辑（main / 路由注册 / 依赖注入装配）；
2. 核心业务模块的**真实实现**（读函数体，不止看函数名）；
3. 数据怎么存（ORM 模型 / 建表 SQL）、接口怎么接（路由 / 控制器 / 参数绑定）；
4. 错误处理与边界的**真实写法**（是否有吞异常、是否回显内部细节）；
5. 配置与密钥的真实读取方式（环境变量 / 配置文件 / 硬编码）。

任何"项目能做什么、怎么做"的结论，最终要能在实际代码里指到对应实现；拿不准的标【待确认】，不臆测。

### 第 2 步：反向梳理功能（从代码反推功能清单）

目标：产出 `docs/requirements/T1-项目需求文档.md`、`docs/requirements/T2-功能清单.md`（按 `T2 模板`）**和 `docs/功能树.md`（按 `T9 模板`）**，把现有功能逐一登记，并先补项目需求文档：

- **先建 T1 项目需求文档**：`docs/requirements/T1-项目需求文档.md`（按 `T1 模板`）——从代码现状 + 开发人确认的意图反向梳理，写清**项目目标、范围边界、核心用户与场景、非功能需求（性能/安全/兼容等），以及「技术约束与前期确认」（T1 第 5 节）**；技术约束项（数据库选型 / 技术栈 / 部署目标 / 外部依赖 / 安全合规级别 / 数据迁移 / 国际化 / 运维监控）须**从实际代码依赖、库表结构、配置文件、部署现状反推**，无法从代码确认的标【待确认】并优先向开发人核实（见总原则 6）；文档未覆盖或不确定的项一律标【待确认】，不臆测。

- **代码↔文档一致性核对（必做）**：将已收集到的需求/设计/README 等文档，逐条与实际代码比对，列出"代码↔文档冲突清单"（文档说 A、代码实际做 B 的项）。冲突项不擅自以任一方为准，提交用户裁定（见总原则 8）。**核对结果须落成文件 `docs/接手冲突核对与解决记录.md`**：每条冲突先写"冲突登记"（文档说法/代码实际/类型），待用户裁定后补全"解决记录"（裁定结论/裁定人/日期/处置动作/关联文件）；文档未覆盖或不确定的项标【待确认】，不臆测。

1. 通读代码模块，按"用户能感知的功能"维度（不是按文件）拆分功能点；
2. 每个功能分配功能编号 F001、F002……（与 T2 模板规则一致）；
3. 每个功能写一句"功能作用"——**以实际代码逻辑为准，不以注释、命名或推测的初衷为准**；命名有歧义时，读实现确认行为；
4. **同步画功能树**：按 模块（M）→ 功能（F）→ 功能点（FP）三层组织，从代码目录/路由结构反推模块划分；**公共组件（认证、通知、导出引擎等跨模块共用部分）必须单列为独立分支**；
5. **梳理依赖关系表**：从代码 import / 公共组件引用中反推"谁依赖谁、谁被谁依赖"，填入功能树——这是后续防乱改的关键输入；
6. 拿不准是不是独立功能的，先归为一个，标记【待确认】。
7. **代码级核对**：第 2 步登记的每个功能 / 接口 / 数据结构，至少抽样回到源码确认"存在且行为一致"；文档与代码不一致的项标注【代码与文档不一致】，不擅自以文档改写对代码的理解。

### 第 3 步：补建功能说明文档（T8，每个功能一份）

对 T2 中每个功能，按 `T8 模板` 产出 `docs/features/F-<编号>-<功能名>.md`：

- **功能作用**：从代码和注释推断，一句话；
- **行为明细**：从代码逻辑提炼输入/处理/输出/边界——这是给未来修改时读的，必须尽量准；
- **依赖关系**：从代码 import/表查询/接口调用中梳理；
- **变更历史**：接手时统一记一条"v1.0 反向梳理自代码，<日期>"。

> 这一步是最耗时的，但也是接手最有价值的产出——补完之后，项目就从"只有代码"变成"代码+功能说明"，后续任何修改都有据可依。

### 第 4 步：补建设计文档（按需，优先级排序）

不是所有设计文档都要一次补齐，按修改紧迫度分批：

| 文档 | 何时补 | 来源 |
|------|--------|------|
| T4 数据库设计 | 即将涉及表变更前 | 反向自现有表结构 |
| T5 接口设计 | 即将涉及接口变更前 | 反向自现有接口 |
| T3 技术需求 | 做较大功能扩展前 | 反向自模块结构 |
| **T11 部署文档** | **尽快补建**（在首次部署/上线前必须完成） | 反向自服务器/容器现状、配置文件、启动脚本；按《27-部署管理规范》第 2 节整理 |

> 部署文档（T11）优先级高于其他设计文档：**没有部署文档，后续每次上线都只能靠猜环境，风险极高**。接手阶段至少把环境清单、服务清单、部署步骤、敏感信息存放位置补齐。

原则：**哪个模块要动，先补哪个模块的文档**——动之前补，不要动完了再补。

### 第 5 步：现状确认（先问开发人，再交用户校准）

补完 T1 + T2 + T8 后，**先把待确认问题向原开发人核实**——他能补上文档没有的实现背景与历史决策；开发人无法解答或已离开的，再整理成清单提交用户校准：

```
已完成项目现状盘点，请校准：
1. 项目需求文档（docs/requirements/T1-项目需求文档.md）已建立，目标与范围已梳理
2. 识别到的功能清单（共 N 个）：<列表>
3. 每个功能的作用已写入 docs/features/F-xxx.md
4. 代码↔文档冲突：共 N 条，详见 `docs/接手冲突核对与解决记录.md`（每条均已登记冲突、并记录用户裁定结论与处置）
5. 待确认问题：<已先问过开发人，仍无法确认的余下项，请逐条给结论>
6. 发现的待修复项：<Bug/隐患清单，请定优先级>
7. 部署文档（docs/deploy/T11-部署文档.md）：<已存在 / 无则按《27-部署管理规范》按现状反向补建，禁止靠聊天记录猜生产服务器/端口/证书>
8. 前期技术约束确认（数据库选型/技术栈/部署/外部依赖/合规级别/迁移/国际化/运维）：已补充进 T1 第 5 节，逐项从实际代码/配置/部署现状核对，无法确认项已标【待确认】并优先问过开发人
确认无误后，本项目即纳入本规范体系，后续开发/变更按总则执行。
```

> **盘点校准后须落盘 `docs/项目记忆.md`**（按 `part2-开发/templates/T-项目记忆（交接文档）模板.md`）：把上方盘点结果聚合成一份项目全景状态叙述 / 交接文档（做过什么、做到哪、已知坑、下一步 + 简短交接速览）。它不是任务清单（那在 开发计划表/CHANGELOG），而是给新人接手、跨团队同步、向领导汇报用的单一可读文档。

用户确认后，项目进入正常流程——此后任何改动都走《30-变更控制规范》。进入正常流程即视为"需求确立"，须按《11-需求分析与确认规范》第五节：向用户**告知后续开发流程**，并**建立开发计划表**（`docs/开发计划表.md`，按 `T-开发计划表模板.md`），把已梳理的功能排期跟踪。

## 三、接手期间的禁止事项

| # | 禁止 | 原因 |
|---|------|------|
| 1 | 盘点期间改代码 | 现状没摸清就改 = 制造新乱子 |
| 2 | 把推测当事实写进文档 | 接手文档必须客观，推测写入会误导后续 |
| 3 | 跳过 T8 直接开始改功能 | 没有功能说明 = 改的时候无据可依 |
| 4 | 一次性试图补全所有设计文档 | 耗时巨大且很多暂时用不到；按需补即可 |
| 5 | 把发现的 Bug 顺手修了 | 只记录、不处理；处理走变更控制 |
| 6 | 仅凭文档/命名/用户口述推断功能，不回代码验证 | 文档会过期、命名会误导、注释会失效；结论必须有代码实证 |
| 7 | 只把文档写成计划/对话，不实际创建文件 | 接手产出必须落地为项目 `docs/` 下真实文件（总原则 7） |
| 8 | 待确认问题既不问开发人也不交用户，直接臆测 | 信息缺失时找对人核实（总原则 6） |
| 9 | 发现代码与文档冲突，直接以一方覆盖另一方不询问用户 | 以哪个为主必须由用户裁定（总原则 8） |
| 10 | 冲突只记在对话/报告里，不落成 `docs/接手冲突核对与解决记录.md` 文件，或冲突有登记无解决记录 | 冲突必须落文档且每条含冲突登记+解决记录（总原则 8） |

- [ ] T9 功能树已产出（含依赖关系表、公共组件分支）？
- [ ] 代码↔文档冲突清单已列出，并询问用户以哪个为主（裁定已记录）？

- [ ] `docs/项目记忆.md` 已建立，写入项目全景状态叙述（做过什么/做到哪/已知坑/下一步）+ 交接速览（按《T-项目记忆（交接文档）模板》）？
- [ ] 每个功能都有对应的 T8 功能说明文档？

- [ ] 待确认问题已列出并交用户？

- [ ] 全程未修改任何代码？
