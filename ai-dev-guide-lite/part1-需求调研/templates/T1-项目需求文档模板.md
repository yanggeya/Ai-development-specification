# T1-项目需求文档（PRD）模板

> 使用说明：AI 调研完成后按本模板生成，保存至 `docs/requirements/PRD-<项目名>-v<版本>.md`。生成后必须提交用户确认，确认后状态改为「已确认」（需求冻结）。【】内为填写指引，产出时删除。
>
> **活文档原则（需求文档的核心定位）**：本模板的**正文始终表示「当前完整需求」**——任何阅读者打开它，应看到一份完整、自洽、最新的需求说明，而不是一堆补丁的堆叠。开发过程中需求持续演进是常态，演进时**直接改写正文对应小节**（第 3 节功能描述、第 2 节角色、第 5 节技术约束、第 6 节范围外、第 7 节开放问题等），让文档始终等于"现在要做什么"。下方「变更记录」**仅为追溯附录**，记"哪一版改了什么、为什么"，**不承载需求本身**——不要把需求改动写成"见变更记录 vX.Y"就完事，正文必须同步更新到位。文档以**单文件持续维护**（版本号在文件内递增），不要为每个修订另存一份独立快照文件；历史版本靠 git / `.backup/`（见《30》§三）追溯即可。

## 5. 技术约束与前期确认（设计前置，需求阶段必须确认）

> 这些项在需求完善阶段即须确认或标【待确认】，随需求一起冻结；设计/编码阶段才发现即视为需求阶段未完善。性能量级与兼容环境见第 4 节非功能需求，本节补「选型级约束」。

| 约束项 | 结论 / 待确认 |
|--------|--------------|
| 数据库选型 | 【SQL/NoSQL、具体产品、新建或复用、是否适配既有 schema】 |
| 技术栈/框架 | 【语言、主框架、前端框架、是否沿用既有栈】 |
| UI 风格与前端规范 | 【风格基调、设计系统/组件库、设计稿来源、响应式与移动端形态、深/浅色、品牌色/Logo/字体】 |
| 部署目标环境 | 【云/SaaS/自托管、OS/容器、域名证书、运维方】 |
| 外部依赖/第三方服务 | 【支付/短信/存储/OAuth 等，必需项 + 密钥/账号提供方】 |
| 安全合规级别 | 【等保级别、是否涉个人信息(PIPL)、数据是否出境、审计留存】 |
| 数据迁移 | 【是否迁旧数据、量级、清洗规则、停机窗口】 |
| 兼容/对接 | 【已有系统/接口协议与鉴权、浏览器/客户端最低版本】 |
| 国际化/多语言 | 【是否需要、涉及语种】 |
| 运维监控 | 【监控/告警/日志归集需求、是否接入既有平台】 |
| 认证与账号体系 | 【登录方式：自研/手机号/第三方 OAuth/SSO；是否需注册、密码策略】 |
| 多租户/数据隔离模型 | 【单租户 / SaaS 多租户；多租户用独立 schema 还是行级隔离】 |
| API 风格 | 【REST / GraphQL / gRPC；前后端交互方式】 |
| 成本/预算上限 | 【预期数据规模与并发、云费用上限、接口限速/配额预期】 |
