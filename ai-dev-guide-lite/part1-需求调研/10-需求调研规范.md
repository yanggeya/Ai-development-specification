# 10-需求调研规范 —— AI 如何获取用户需求

> **本文件规定 AI 在接到新需求后的提问方法。目标：问出真需求，问全关键信息，禁止臆测。**

- 版本：v1.3
- 前置阅读：`00-总则.md`
- 适用场景：用户提出新项目、新功能、新想法，需求尚未形成文档时
- 参考底稿：`13-需求工程参考与方法论.md`（生成 T1/T2 时可对齐业界实践，非强制）

---

## 一、提问总原则

1. **先理解，再提问，最后复述**。提问前先消化用户已说的内容；能从已有信息推断的不问，需要决策的必须问。
2. **禁止臆测**：用户没说、文档没写的关键信息，一律提问确认，不得假设后直接开发。
3. **一次聚焦一层**：按层级递进提问，不跨层、不混杂。
4. **控制提问数量**：每轮提问不超过 5 个问题，优先问影响架构和数据结构的；次要细节可标记为「后续确认」。
5. **提供选项而非开放题**：能给出候选项的尽量给选项（含推荐项），降低用户回答成本。
6. **复述确认**：每轮调研结束前，用自己的话复述一遍理解，请用户纠正。

## 二、分层提问法（由粗到细五层）

### 第 1 层：业务目标
- 这个功能/项目要解决什么问题？
- 给谁用？用了之后达到什么效果？
- 怎么判断做成功了？（可量化的成功标准）

### 第 2 层：用户角色
- 有哪几类使用者？各自的权限差异？
- 每类角色的典型操作是什么？

### 第 3 层：核心场景
- 完整走一遍主流程：用户从哪进入 → 做什么操作 → 系统怎么响应 → 得到什么结果？
- 高频操作是哪些？（决定优化重点）
- 有没有特殊/例外场景？（如批量、定时、离线、并发）

### 第 4 层：功能点拆解
- 把场景拆成一个个可独立验收的功能点；
- 每个功能点确认：输入是什么、处理规则是什么、输出是什么；
- 边界条件：数据量级、空数据、超长输入、并发冲突怎么处理？

### 第 5 层：非功能需求
- 性能：响应时间要求？数据量级（行数/并发数）？
- 安全：哪些数据敏感？谁不能看什么？
- 兼容：需要对接的已有系统/接口？浏览器或客户端环境？
- 数据：数据从哪来？历史数据要不要迁移？

### 第 6 层：前期技术约束（设计前置，需求完善时必须补充）

> 这些项一旦定错，后期返工成本极高——必须在需求完善阶段就问清或显式标【待确认】，并写入 T1「技术约束与前期确认」章节，随需求一起冻结；不要等到设计/编码阶段才浮现。

逐项确认（问清结论或标记待定）：
- **数据库选型**：用 SQL 还是 NoSQL？具体产品（MySQL/PostgreSQL/MongoDB…）？新建库还是复用既有库？是否需适配已有 schema？
- **技术栈/框架**：开发语言与主框架？前端框架（如有）？是否沿用项目既有技术栈（接手项目尤其要确认）？
- **UI 风格与前端规范**（仅含前端/界面项目，必答）：UI 风格基调（后台管理风 / 营销官网风 / C 端产品风 / 其他）？是否遵循某设计系统或组件库（Ant Design / Element Plus / Material / Tailwind 自搭 / 自有 UI 规范）？**有无设计稿来源**（Figma / 蓝湖 / UI 规范图 / 无设计稿由 AI 自由发挥——后者须用户给参考站或风格关键词）？是否需响应式（桌面优先 / 移动优先 / 都要）及移动端形态（H5 / 小程序 / App）？是否支持深色模式？品牌主色 / Logo / 字体等视觉规范是否强制？——这些决定界面实现基线，**无设计稿时必须在需求期定风格关键词，禁止编码阶段自创风格**。
- **部署目标环境**：部署到云/SaaS 还是自托管？OS/容器？域名与证书谁提供？生产环境由谁运维？
- **外部依赖/第三方服务**：是否依赖支付/短信/邮件/地图/对象存储/OAuth-SSO/消息队列等？哪些必需？API 密钥或账号由谁提供？
- **安全合规级别**：是否涉等保（几级）？是否处理个人信息/重要数据（受 PIPL 约束）？数据是否允许出境？审计日志留存要求？
- **数据迁移**：是否需从旧系统迁数据？量级、清洗规则、可接受停机窗口？
- **兼容/对接**：需对接的已有系统/接口（协议、鉴权方式）？浏览器/客户端最低版本？
- **国际化/多语言**：是否需要多语言？涉及哪些语种？
- **运维监控**：是否需要监控/告警/日志归集？是否要接入既有运维平台？
- **认证与账号体系**：登录方式（自研账号密码 / 手机号 / 第三方 OAuth / 企业微信等 SSO）？是否需注册流程、密码策略（复杂度/有效期）？这决定用户表结构、接口设计与权限模型，必须在需求期定；
- **多租户 / 数据隔离模型**：单租户还是 SaaS 多租户？多租户用独立 schema 还是行级隔离（tenant_id）？决定库结构根本形态，后期加成本极高；
- **API 风格**：对外接口用 REST / GraphQL / gRPC？前后端如何交互？决定 T5 接口设计基线；
- **成本 / 预算上限**：预期数据规模与并发？云费用是否有预算上限、对外暴露接口的限速/配额预期？决定架构选型与部署期硬约束（见《27》）。

> 性能量级与兼容环境已在第 5 层非功能需求覆盖，本层补「选型级约束」。任一项用户未给结论且影响架构的，标记为【待确认】列入 T1 开放问题，禁止臆测。

## 三、提问检查清单（形成需求文档前逐项过一遍）

- [ ] 业务目标一句话说清楚了？
- [ ] 用户角色和权限差异明确了？
- [ ] 每个核心场景走通了（输入→处理→输出）？
- [ ] 每个功能点可独立验收？
- [ ] 边界条件与异常处理有结论？
- [ ] 非功能需求（性能/安全/兼容/数据）有结论或已标记待定？
- [ ] 前期技术约束（数据库选型/技术栈/部署/外部依赖/合规级别/迁移/国际化/运维/认证体系/多租户隔离/API 风格/成本预算/UI 风格与前端规范）已问清或标【待确认】（见第 6 层）？
- [ ] 做什么/不做的边界（范围外事项）明确？
- [ ] 已向用户复述理解并获得确认？

## 四、调研产出

调研完成后，按《11-需求分析与确认规范》整理，产出：

> 生成 T1/T2 时，可参考《13-需求工程参考与方法论》中的框架（优先级 / 验收标准 / PRD 结构）提升质量，**非强制套用**。

1. **澄清问答记录**（附在 PRD 附录或对话中确认）；
2. **《T1-项目需求文档》**（使用 `templates/T1-项目需求文档模板.md`）；
3. **《T2-功能清单》**（使用 `templates/T2-功能清单模板.md`）。

三者经用户确认后，需求冻结，进入开发阶段。

## 五、典型反例（禁止的做法）

| 反例 | 问题 | 正确做法 |
|------|------|---------|
| 用户说"做个登录"，AI 直接开始写 | 未澄清登录方式、角色体系 | 先问：账号密码/手机号/企业微信？要不要注册流程？角色有几种？ |
| 一次抛出 15 个问题 | 用户疲劳，随意回答 | 分轮次、给选项，每轮 ≤5 个 |
| 把不确定的细节记为"应该就是这样" | 臆测进入文档 = 后期返工 | 标记为【待确认】，列出问题清单集中确认 |
| 只记录做什么，不记录不做什么 | 范围蔓延，越做越大 | 明确「范围外事项」写入 T1 |
