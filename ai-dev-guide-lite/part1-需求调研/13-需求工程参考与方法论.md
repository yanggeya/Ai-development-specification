# 13-需求工程参考与方法论（AI 生成需求文件的参考底稿）

> **定位**：本文件是 AI 在生成 T1（项目需求文档）/ T2（功能清单）时的**可选参考底稿**，**不是强制门禁**。
> AI 不依赖本文件也能工作；但当需要提升需求质量、对齐行业通行实践时，可在此择需取用。
> 若项目已有既定方法论（公司 PRD 模板、既定优先级体系等），**以项目为准**，本文件退为补充。

- 版本：v1.0
- 前置阅读：`10-需求调研规范.md`、`11-需求分析与确认规范.md`
- 何时用：生成或修订 T1 / T2 时，作为框架与术语坐标；尤其当用户需求模糊、优先级难定、验收标准写不清时

---

## 一、需求分类框架

| 类别 | 说明 | 落点 |
|------|------|------|
| 业务需求（BRD） | 组织层面的目标与价值 | T1「业务目标 / 成功标准」 |
| 用户需求 | 角色想完成的任务 | T1「用户角色 / 核心场景」 |
| 系统需求（SRS） | 系统须具备的能力 | T2 功能点 + 验收标准 |
| 功能性需求 | 系统"做什么" | T2 功能点 |
| 非功能性需求（NFR） | 系统"做得怎样" | T1「非功能需求」；对齐 ISO/IEC 25010 八类质量特性 |

**ISO/IEC 25010 质量特性（写 NFR 时的检查清单）**：
功能适用性、性能效率、兼容性、可用性、可靠性、安全性、可维护性、可移植性。
> AI 起草非功能需求时，优先从这八类里点出本项目关心的几项，避免"系统要稳定"这类空话。

---

## 二、需求挖掘框架（辅助《10》五层提问）

- **5W1H**：What / Who / Why / When / Where / How —— 用于补全场景与边界。
- **Jobs-to-be-Done（JTBD）**：用户"雇用"产品完成什么任务、替代了什么、什么算成功。比"功能列表"更能挖出真实动机。
- **用户故事**：`As a <角色> I want <能力> so that <价值>` —— 每个 T2 功能点可附一句，帮助对齐价值。
- **痛点—场景—收益**三角：记录每个需求的来源痛点、发生场景、预期收益，防止"为做而做"。

---

## 三、优先级框架

| 框架 | 维度 | 适用 |
|------|------|------|
| **MoSCoW** | Must / Should / Could / Won't（本期） | 快速分档，和现有 P0/P1/P2 可对应 |
| **RICE** | Reach×Impact×Confidence / Effort | 多需求排期、资源受限时量化排序 |
| **Kano** | 基础型 / 期望型 / 兴奋型 | 判断是否"不做用户就流失"（基础型≈P0） |

**与现有 P0/P1/P2 的映射建议**（非强制）：
- 基础型需求 + 主流程必需 → P0
- 期望型 + 核心价值 → P1
- 兴奋型 / 锦上添花 → P2
> 若用户已用 P0/P1/P2 表达清晰，不必强行换算 RICE/Kano，避免增加阅读负担。

---

## 四、验收标准写法

- **INVEST**：Independent 独立 / Negotiable 可协商 / Valuable 有价值 / Estimable 可估算 / Small 小 / Testable 可测。用于检验每个 T2 功能点是否拆解到位。
- **Given-When-Then（BDD）**：
  - Given（前置）：系统处于什么状态
  - When（操作）：用户做了什么
  - Then（结果）：系统应怎样响应
  - 例：`Given 资产名为空 When 用户点击搜索 Then 列表显示"无匹配结果"提示且耗时<1秒`
- **可量化成功标准**：呼应 T1「成功标准」字段，用数字而非形容词（"录入耗时 30min→5min"而非"更快"）。

## 五、PRD / 需求文档结构参考

| 来源 | 要点（对照 T1 模板字段） |
|------|------------------------|
| **Google PRD 经典结构** | 背景与目标、问题与非目标、解决方案概述、成功指标、里程碑、风险 —— 对应 T1 业务目标/范围外/成功标准 |
| **IEEE 830 SRS 大纲** | 引言、总体描述、功能需求、性能需求、设计约束、验收准则 —— 对应 T1 章节结构 |
| **OKR / HEART 指标** | 用可度量指标定义"成功"（Objectives+Key Results / 满意度/参与度等） |

> T1 模板已覆盖上述主干；本表用于 AI 自查"是否漏了关键章节"，不要求改写模板。

## 六、范围与基线管理

- **MVP 与完整版边界**：明确本期最小可用范围，避免一次铺太大。
- **需求基线冻结**：T1/T2 确认后即冻结，后续变更走《30-变更控制规范》—— 与《11》冻结机制一致。
- **范围蔓延防护**：所有"不做"的事项写入 T1「范围外事项」，所有"待定"写入「开放问题」。

---

## 七、给 AI 的使用约定

1. 本文件是**参考坐标，不是检查清单**；生成 T1/T2 时择需对齐，不强行套用。
2. 项目已有模板 / 方法论时，**以项目为准**，本文件退为补充。
3. 不把用户看不懂的框架术语写进交付物；若引用（如 Kano、RICE），需一句话解释。
4. 不得因对齐框架而降低可读性、增加用户审阅负担。
5. 当《10》《11》与本文件冲突时，以《10》《11》的强制要求为准。

## 附：场景 → 可用框架 速查

| 遇到的困难 | 可参考本文件 |
|-----------|-------------|
| 用户只说"做个 XX"，目标模糊 | 一（分类）、二（JTBD/5W1H） |
| 功能很多，分不清轻重 | 三（MoSCoW/RICE/Kano） |
| 验收标准写不清（"好用"） | 四（INVEST/Given-When-Then） |
| 不知道 PRD 还缺什么章节 | 五（Google PRD / IEEE 830） |
| 需求越做越大收不住 | 六（MVP/范围外/冻结） |
| 非功能需求空泛 | 一（ISO 25010 八类） |
