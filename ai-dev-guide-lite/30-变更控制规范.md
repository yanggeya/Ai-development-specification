# 30-变更控制规范 —— 防止乱改的硬性流程

> **任何修改任务（改功能、修 Bug、调整行为）开始前，必须读本文件并严格执行。本文件的目标：改得准、改得全、改得可追溯，杜绝"顺手乱改"。**

- 版本：v1.9
- 前置阅读：`00-总则.md`

---

## 〇、适用范围（先判定本文件管不管这件事）

| 任务            | 是否走本文件        | 路径                                                       |
| ------------- | ------------- | -------------------------------------------------------- |
| 修改/删除已有功能的行为  | **是**（本文主体流程） | 定位 → 评估 → 锚点 → 文档先行 → 代码                                 |
| Bug 修复（不改行为）  | 走第五节简化流程      | 现象/根因/方案 → 锚点 → 修复 → CHANGELOG                           |
| **安全漏洞修复**（来自 T10） | **是**，主体流程从简但记录不减 | 见下方"安全漏洞修复特别说明"                                   |
| 冻结项目上**新增**功能 | 不走修改流程，但需登记   | 按《10》做迷你调研 → 更新 T1/T2/T9 登记（登记本身记 CHANGELOG）→ 按总则分级走开发流程 |
| 全新项目首批功能      | 否             | 走 part1 完整调研 → part2 开发                                  |

**配置 / 环境变更的额外义务**（很容易漏）：改端口、环境变量、依赖中间件、证书、部署方式等，除走本文件流程外，**必须同步更新 `docs/deploy/T11-部署文档.md` 对应小节**，并记入 T11 的部署记录——否则部署文档会与实际环境脱节，下次部署按过时文档操作就会出事。

**安全漏洞修复特别说明**（《26-安全测试规范》产出 T10 后的修复）：
- 漏洞在 T10 中已有复现步骤与证据 → 影响评估可引用 T10 条目，不重复写；
- 基线锚点、范围锁定、CHANGELOG 记录**一项不能少**——安全修复也是代码修改，同样禁止顺手乱改、禁止夹带无关修复；
- 修复完成后必须回《26-安全测试规范》**复测**并在 T10 登记复测结果，修复才算闭环。

**判定技巧**：问"这个功能在 T2 功能清单里存在吗？"——存在且要改它的行为 → 本文件；不存在 → 新增，走登记路径。

## 一、修改前的强制动作（缺一不可）

### 1. 定位功能与读取现状

接到修改指令后，AI 必须：

1. **先在 `docs/功能树.md` 中定位目标节点**（模块 → 功能 → 功能点），并查依赖关系表确认波及范围；树上未涉及的分支一律不动。找不到目标节点 → 停下，先补登记或向用户确认，禁止凭感觉定位；
2. 在 T2 功能清单中定位该功能的功能编号（如 F003）；
3. **读取 `docs/features/F-003-<功能名>.md` 功能说明文档**，理解该功能当前的作用、行为、依赖；
4. 读取相关设计文档（T3/T4/T5）中涉及该功能的部分；
5. **读取目标功能的 T8 功能说明文档现状**——这是理解功能、做影响评估的事实基线（T8 路径见 `docs/features/F-<编号>-<功能名>.md`，编号与 T2 一致）；
6. 阅读现有代码，确认代码与 T8 文档描述是否一致；
7. 若本项目存在 `docs/开发计划表.md`，读取它定位本任务在排期中的位置与依赖任务，确认本次变更对里程碑 / 排期的影响（无此文档则跳过，或确认本项目是否适用计划表；计划表补建见《11-需求分析与确认规范》）。

**若功能说明文档（T8）不存在**：先补建 T8 功能说明文档（按现状代码反向梳理），经用户确认后再进入修改流程。

**若代码与 T8 文档不一致**：暂停修改，向用户报告差异，待确认以哪边为准并修正后再继续。

### 2. 影响评估（必须输出给用户）

修改动手前，输出一份《变更影响评估》，包含：

| 评估项   | 内容                           |
| ----- | ---------------------------- |
| 修改目标  | 用户要改成什么样（一句话）                |
| 涉及功能点 | 功能编号 + 名称（可能波及的关联功能也要列出）     |
| 功能树定位 | 模块 → 功能 → 功能点路径；依赖关系表中受波及的节点 |
| 涉及文档  | 哪些 T3/T4/T5/T8/功能树需要更新       |
| 涉及数据库 | 表/字段是否有增删改                   |
| 涉及接口  | 哪些 API 的请求/响应会变化             |
| 兼容性影响 | 旧数据是否需迁移、已有调用方是否受影响          |
| 回滚方式  | 改坏了怎么恢复                      |

### 3. 范围锁定（修改文件清单）

AI 必须列出**本次将修改的全部文件清单**（代码 + 文档），交用户确认：

```
本次修改将触及：
1. src/modules/xxx/service.py        —— 修改分页逻辑
2. docs/features/F-003-资产列表.md   —— 同步更新功能说明
3. docs/tech/T5-接口设计-资产模块.md —— 更新接口参数说明
```

**清单经用户确认后即为修改边界。** 开发过程中发现需要改清单外的文件 → 立即停下，向用户说明原因并请求追加，禁止先斩后奏。

## 二、修改执行的顺序（文档先行）

```
变更影响评估 → 用户确认范围
      ↓
⓪ 打基线锚点（git 提交/备份，见第三节）
      ↓
① 先更新设计文档（T3/T4/T5 中受影响部分）→ 阶段提交（回退点 1）
      ↓
② 修改代码 → 阶段提交（回退点 2）
      ↓
③ 更新功能说明文档 T8（功能作用、行为变化、影响范围）→ 阶段提交（回退点 3）
      ↓
④ 补充/调整测试用例并验证
      ↓
⑤ 写入 CHANGELOG（含回退锚点信息）
      ↓
报告完成（附：改了什么、哪些文档已同步、如何回退、遗留问题）
```

**规则：文档先行，代码随后。** 数据库变更必须先改 T4 文档再写迁移脚本；接口变更必须先改 T5 文档再改代码。

### 项目文档同步门禁（功能文档 / 项目记忆随代码同步，含接手联动）

修改功能 ≠ 只改代码。功能说明文档（T8）是功能级唯一事实源，**`docs/项目记忆.md` 是项目级状态叙述事实源**，二者都必须与代码 / 进展保持同步，否则视为修改未完成。强制执行：

- **修改前：先读 T8 现状**。进入修改流程第一步必须读取目标功能的 `docs/features/F-xxx.md` 现状（见本节 §1 第 5 步），作为理解功能、做影响评估的事实基线；T8 不存在 → 先反向补建；T8 与代码不一致 → 暂停报告（见 §1）。
- **修改中：T8 是独立阶段提交点**。按上面流程图，T8 更新作为第 ③ 步独立阶段提交（回退点 3），不得与设计文档或代码混在同一提交，保证"文档已改、代码未改"可独立回退。
- **修改后：回填 + 校验**。代码完成后必须：① 在 T8「变更历史」追加一行（日期 / 版本 / 变更内容 / 依据）；② 同步更新 T8 作用 / 行为 / 依赖 / 权限 / 配置等随变更改写的对应小节；③ 自检"只读 T8 能否推导出本次变更后的行为"——不能则继续补写；④ **本次任务一旦带来项目进展 / 状态变化，必须同步更新 `docs/项目记忆.md`**——包括但不限于：新功能开发完成 / 模块交付、已有功能修改导致行为变化、重要 Bug 修复闭环、关键决策裁定、上线 / 部署。**更新范围**：「二、开发进展与当前状态」「三、近期重要变更」（关联 `CHANGELOG.md`）「六、本文件变更记录」。项目记忆是给人 / 接手 / 领导看的全景叙述，不得滞后于真实进展。
- **完成门禁（任一不满足 = 任务未完成，不得报告"修改完成"）**：
  - [ ] T8 已更新且变更历史已追加；
  - [ ] 功能树（T9）节点 / 依赖已同步（《总则》原则 7）；
  - [ ] `docs/项目记忆.md` 已更新（本次带来进展/状态变化：新功能完成、模块交付、重要修复闭环、决策裁定等）；
  - [ ] `docs/开发计划表.md` 已同步（如本项目使用计划表且本次涉及排期 / 任务状态变动）；
  - [ ] CHANGELOG 已写（含回退锚点）。
- **接手项目联动**：接手项目反向补建的 T8 与 `docs/项目记忆.md` 同样适用本门禁（二者即唯一事实源，非临时文档）。若本次修改涉及《接手冲突核对与解决记录》中某条已解决冲突对应的功能 / 代码，须在该记录对应条目下追加"后续变更"备注（日期 / 变更摘要 / 是否推翻原裁定），**不得丢弃接手冲突记录**。
- **需求演进同样适用本门禁（且不是"只记修订"）**：当需求本身演进（新增 / 修改 / 删除功能、调整范围外、技术约束变化、角色变化）时，**T1 项目需求文档与 T2 功能清单的「正文」必须改写为当前完整需求**——第 3 节功能描述、第 2 节角色、第 5 节技术约束、第 6 节范围外、第 7 节开放问题等直接更新；T1 / T2 读起来始终是"现在要做什么"，而非"原始需求 + 修订堆叠"。CHANGELOG / T1「变更记录」仅作追溯附录（记"变了什么、为什么"），**不承载需求正文**。
  - 若需求变更**已落到代码** → 本项（T1/T2 正文更新 + CHANGELOG）与上面"功能修改"的 T8 / 功能树 / 开发计划表 / 项目记忆同步一并完成；
  - 若需求变更**尚未落码** → 本项即完成门禁，不强制 T8（功能尚未实现，无 T8 可同步）。
  - 完成门禁新增勾选项：`[ ] （需求演进）T1/T2 正文已改写为当前完整需求，而非仅追加修订记录；`

## 三、变更过程记录与回退（每次变更强制执行）

> 目标：任何一次变更改坏了，都能**一步退回到变更前的状态**。回退能力靠事前锚点，不靠事后补救。

### 1. 变更前打基线锚点（动手前必做）

| 环境有 git                                             | 环境无 git                                     |
| --------------------------------------------------- | ------------------------------------------- |
| 确认工作区干净后记录当前 commit id（或打 tag：`before-F003-export`） | 把本次将修改的每个文件备份到 `.backup/<日期>-<变更标题>/`，保留原文件 |

基线锚点必须写入 CHANGELOG 条目的「回退锚点」字段，**没有锚点不得开始修改**。锚点打完后**立即在 CHANGELOG 写入本条变更（状态：进行中）**，完成后再改为「生效中」——这是跨会话识别未完成变更的依据。

### 2. 分步提交形成回退点

禁止把一次变更的全部改动攒成一大坨。按流程图的阶段分别提交（git commit 或备份目录），每步一个可独立回退的点：

- 回退点 1：文档更新（纯文档，回退不影响代码）
- 回退点 2：代码修改（回退即回到"文档已改、代码未改"状态）
- 回退点 3：T8 同步更新

> 提交信息格式：`F003-export: ① 文档更新` / `F003-export: ② 代码实现` / `F003-export: ③ T8 同步`。

### 3. 文档旧版本保留

文档更新**不覆盖历史**：

- 文档头部的「变更记录」表每版追加一行（版本、日期、变更内容），旧版内容保留在 git 历史或备份目录中；
- 重大改版（如 T4 表结构大改）时，旧版另存为 `docs/archive/<原路径>/T4-xxx-v1.md` 后再写新版。

### 4. 回退操作

回退时按相反顺序执行，并遵守：

1. **先回代码，再回文档**（或整体回到基线锚点）；
2. **涉及数据库的变更不能简单回退代码**——必须同时执行 T4 中对应的回滚脚本，数据先行；
3. 回退完成后：更新 CHANGELOG 记一条「已回退」、T8 恢复为回退前版本、T2 功能状态改回。

## 四、禁止事项（防乱改红线）

| # | 禁止行为               | 正确做法                                   |
| - | ------------------ | -------------------------------------- |
| 1 | 顺手重构、重命名、调整无关代码格式  | 只改清单内文件；发现的代码问题单独报告，由用户决定是否另开任务        |
| 2 | 擅自升级依赖版本、更换第三方库    | 报告动机与风险，经确认后作为独立变更执行                   |
| 3 | 修改公共组件/工具类而不评估全局影响 | 公共组件修改必须列出所有使用方并逐一评估                   |
| 4 | 删除"看起来没用"的代码、注释、配置 | 先确认用途（查引用、问用户），确认无用后才可删，且记录入 CHANGELOG |
| 5 | 修改功能说明文档之外的功能行为    | 行为变化必须先在文档中体现并确认                       |
| 6 | 改了代码不更新 T8 功能说明    | **改代码不改 T8 = 任务未完成**                   |
| 7 | 一次修改夹带多个未确认的需求     | 一个变更任务只做一件事，多需求分开评估                    |

### 冻结模式与破坏性/不可逆操作约束（硬规则，不可绕过）

- **冻结/只读模式**：用户声明"冻结 / 不要改动 / 不要动数据库"时，所有写操作（代码、数据、配置、文档）一律禁止；AI 不得"清理""优化"冻结范围内的任何内容。AI 自述"已做 / 已恢复 / 已销毁"不可信，必须以 git diff / 审计日志 / 实际数据库查询为准；严禁伪造执行结果或数据（触犯红线 R17）。
- **破坏性/不可逆操作**：删库、删表、删云资源、批量 DELETE/UPDATE/DROP、覆盖式迁移等，必须取得人工**显式确认的目标与影响范围**后才可执行；AI 代理默认只读，绝不持有生产写权限；批量数据操作须事务化 + 先 dry-run 估算影响行数 + 先独立备份，生产数据操作需人工审批。

## 五、Bug 修复（P3 小改动）简化流程

不改变功能行为的 Bug 修复可走简化流程，但仍需：

1. 说明 Bug 现象、根因、修复方案（一段话即可）；
2. 修复前打基线锚点（git commit 或文件备份）；
3. 修复后验证原 Bug 已消除、未引入新问题；
4. 记入 CHANGELOG（日期、现象、根因、修复方式、回退锚点）。

**升级规则**：修复过程中发现需要改变功能行为才能解决 → 停下，升级为「修改功能」流程，重新评估确认。

## 六、变更记录格式（CHANGELOG）

每次变更在 `CHANGELOG.md` 追加一条：

```markdown
## [2026-09-02] F003 资产列表增加导出功能（P2）

- 更类型：功能修改
- 变更内容：资产列表新增"导出 Excel"按钮及后端导出接口
- 影响文档：T5-接口设计-资产模块.md、F-003-资产列表.md
- 数据库变更：无
- 回退锚点：基线 commit a1b2c3d（before-F003-export）；回退点：①文档 ②代码 ③T8
- 回退方式：回退代码与文档至基线 commit；无数据迁移
- 状态：进行中（变更开始时即写入本条，完成前保持此状态）/ 生效中 / 已回退（日期+原因）
```

## 七、自检清单（报告完成前）

- [ ] 已在功能树中定位目标节点并查依赖关系表？定位记录已填？
- [ ] 影响评估已做且范围清单经用户确认？
- [ ] 动手前打了基线锚点并记入 CHANGELOG？
- [ ] 文档/代码/T8 分步提交，形成独立回退点？
- [ ] 只修改了清单内的文件？
- [ ] 设计文档（T3/T4/T5）先于代码更新？
- [ ] 功能说明文档 T8 已同步更新？
- [ ] 功能树已同步更新（节点/依赖/定位记录）？
- [ ] CHANGELOG 已记录（含回退锚点与回退方式）？
- [ ] 回退方式实际可行（涉及数据库时回滚脚本已备好）？
- [ ] 发现的清单外问题已单独报告而非顺手处理？
