# 26-安全测试规范 —— 功能渗透测试流程

> **本文件规定功能开发完成、功能测试（T6）通过后的安全测试要求。核心规则：安全测试不通过的功能不得进入上线流程；发现的安全漏洞按严重程度分级处置，修复必须走《30-变更控制规范》。**

- 版本：v1.7
- 前置阅读：`00-总则.md`、`24-测试与验收规范.md`、对应 T5 接口设计文档
- 产出文档：T10 安全测试报告（保存至 `docs/test/T10-安全测试-<功能名>-<日期>.md`）

---

## 一、安全测试在标准开发流程中的位置

```
需求冻结 → T3/T4/T5 设计 → 编码 → 功能测试（T6，24规范）
      ↓
安全测试（T10，本规范）← 功能测试通过后才进入
      ↓
漏洞处置（严重/高危必须修复；修复走 30-变更控制）→ 复测
      ↓
上线方案（T7，25规范）← 上线准入必须包含 T10 结论
```

**为什么在功能测试之后**：功能不稳定时做安全测试，漏洞结论会被功能缺陷干扰；功能测试通过意味着行为已固化，此时验证的是"固化的行为是否安全"。

**验证手段对齐微软 SDL「验证」阶段**：本规范 T10 属于验证环节的人工安全测试部分；完整的 SDL 验证还应包含自动化手段，项目具备 CI/CD 时须作为门禁内置——
- **SAST 静态分析**：代码提交/构建时自动扫描（含密钥扫描、依赖漏洞），已知高危直接阻断合并；
- **DAST 动态分析**：对测试环境运行的应用做主动探测；
- **模糊测试（Fuzzing）**：对 API/解析器投喂畸形输入，验证错误处理与抗注入能力；
- **人工代码审查（职责分离）**：合并前由非作者审查安全符合性（呼应 SDL 的 separation of duties——审查者 ≠ 开发者）；
- **配置校验**：对比生产配置与安全基线（默认配置加固清单见《23》§5.2）；
- **组件治理（CG）**：开源组件检测（版本/漏洞/许可证），见 H8、I1。
无 CI 时按《24》最小门禁要求，至少落地 SAST + 密钥扫描 + 人工审查（两人或 AI+人工）。项目具备 CI/CD 且 `docs/tech` §8 启用强验证时，上述手段的管线编排与合并门禁见《29-持续集成与自动化验证规范》（可选模块）。

## 二、测试范围与分级

| 级别 | 是否做安全测试 | 范围 |
|------|--------------|------|
| **P1 重大功能** | **必须**，完整 T10 报告 | 新模块全部接口 + 鉴权边界 + 数据变更路径 |
| **P2 一般功能** | **必须**，简版 T10（可记入 CHANGELOG） | 本次新增/修改的接口 + 越权抽查 |
| **P3 小改动** | 免测，但**涉及以下任一情形时升级为 P2 处理**：动了鉴权/权限判断逻辑、动了输入解析、动了文件/命令执行相关代码 |
| **所有新增接口** | 无论级别，**新增对外接口必须做基础安全项检查**（见第三节 G1-G5） |

**触发重新安全测试的条件**：功能变更涉及鉴权逻辑、数据结构、外部输入处理时，即使原功能已测过，本次变更也必须针对变更点补测（在变更影响评估中列出）。

## 三、测试项清单（按优先级执行）

### G 组：基础安全项（每个新增接口必测，P1/P2/P3 新接口均适用）

| # | 检查项 | 测试方法 | 通过标准 |
|---|--------|---------|---------|
| G1 | 未授权访问 | 不带凭证直接请求接口 | 返回 401/403，不返回业务数据 |
| G2 | 越权访问（横向） | 用用户 A 的凭证访问用户 B 的资源（改 ID 参数） | 拒绝；返回 403 或空数据，不泄露 B 的数据 |
| G3 | 越权访问（纵向） | 用普通用户凭证访问管理接口 | 拒绝 |
| G4 | 注入类（SQL/命令/模板） | 输入 `'`、`"; ls`、`${7*7}`、`{{7*7}}` 等载荷 | 无报错回显、无命令执行结果、无模板渲染结果；参数化查询/白名单生效 |
| G5 | 敏感信息泄露 | 检查响应体、报错信息、调试接口 | 无密码明文、无密钥/token、无堆栈信息、无内部 IP |
| G6 | 密钥硬编码 | 扫描代码与配置 | 无明文密钥/token/证书私钥；密钥须走环境变量/密钥管理（声明即用环境变量，不落代码与仓库） |

### H 组：深度测试项（P1 必测，P2 按功能涉及面选取）

| # | 检查项 | 适用场景 | 测试要点 |
|---|--------|---------|---------|
| H1 | 认证与会话 | 登录、token、会话 | 弱口令策略、token 过期机制、登出后 token 是否失效、验证码防爆破 |
| H2 | 权限矩阵遍历 | 多角色系统 | 按角色×接口矩阵逐格验证，无遗漏 |
| H3 | SSRF | 接受 URL 参数的功能 | 请求内网地址（127.0.0.1、169.254.169.254 等）应被拦截 |
| H4 | 文件上传 | 上传功能 | 上传可执行文件/超大文件/伪造后缀应被拦截；上传路径不可控 |
| H5 | 反序列化 / XXE | 接受 XML/序列化数据 | 恶意 payload 无副作用 |
| H6 | 批量拉取 / 爬取防护 | 列表、导出类接口 | 无分页上限的接口有单次量限制；导出有权限与频率控制 |
| H7 | 业务逻辑 | 状态流转、金额/数量类 | 重复提交、负数、跳步操作、并发竞态 |
| H8 | 依赖与供应链安全 | 所有功能 | ①已知组件 CVE（框架/库高危漏洞）；② 新增依赖存在性校验（确认包真实存在、维护者可信）；③ lockfile+hash 校验，禁止未锁定依赖；④ 安装脚本（postinstall）与依赖来源扫描，防供应链投毒 |

> 项目有安全基线/合规要求的（等保、行业规范），在【项目安全要求填空位：______】（见 `docs/tech/技术栈约定.md`，由 AI 接入时与用户确认后写入）补充额外检查项。

### I 组：合规与供应链（P1/P2 涉及第三方代码、对外发布、处理用户数据时必查）

| # | 检查项 | 适用场景 | 测试要点 |
|---|--------|---------|---------|
| I1 | 许可证合规 | 引入第三方库、复制代码片段 | 跑许可证扫描（FOSSA/Snyk/Black Duck）；强 copyleft（GPL 类）依赖须人工评审，避免"传染"致整个代码库须开源 |
| I2 | 代码来源/查重 | AI 生成或复制的代码 | 启用代码引用/查重过滤，禁止逐字复现受版权保护的第三方代码而不注明来源/许可证 |
| I3 | 数据不出域 | 使用 AI 辅助开发 | 禁止把公司专有代码、业务逻辑、个人/敏感数据粘贴进公共 AI 工具（触犯红线 R14）；用企业级数据隔离 |
| I4 | 人类创造性记录 | 主张 IP/版权时 | 保留"哪些是人写、哪些是 AI 生成"的记录，关键决策有可记录的人类创造性投入，便于确权 |

### 外部输入当指令防护（开发约束，非测试项）

AI 编写的代码**不得把外部不可信输入当作指令执行**：
- PR/issue 标题、MCP 配置、Webhook 回调体、网页抓取内容等，只能作为数据解析，绝不能拼接进 shell/命令/脚本执行，也不能被当作系统提示词；
- CI 中的自动化 bot 不持有写权限（不推送、不发布、不改配置），信任文件夹须显式确认且限定范围；
- 写文件前必须解析符号链接真实目标，禁止向工作区之外（如 `~/.ssh`、`/etc`）写入；确认 UI 须展示真实目标路径。

## 四、漏洞分级与处置

| 级别 | 定义 | 典型示例 | 处置要求 |
|------|------|---------|---------|
| **严重** | 可直接获取系统权限/大量敏感数据 | SQL 注入可拖库、未授权管理接口、RCE | **立即停止上线**，修复并复测通过后重新评估上线 |
| **高危** | 可越权/绕过核心控制 | 横向越权读他人数据、任意文件读取 | 上线前必须修复 + 复测 |
| **中危** | 有利用条件但影响可控 | 敏感报错信息、token 不过期 | 上线前修复；确因工期延后的须用户书面确认接受风险 |
| **低危** | 加固建议类 | 缺安全响应头、弱密码策略提示 | 可随下个迭代修复，登记跟踪 |

**处置纪律**：
1. 发现漏洞 → 先记录（现象、复现步骤、证据），**禁止顺手直接改代码**——漏洞修复也是代码修改，走《30-变更控制规范》；
2. 修复后必须**复测**：验证漏洞消除且未引入新问题（重跑 G 组基础项）；
3. 所有漏洞（含低危）登记入 T10 报告，不遗漏、不美化；已修的标"已修复+复测通过"，未修的标状态与原因；
4. **向用户报告时如实呈现**，严重/高危漏洞必须在报告中置顶醒目标注。

## 五、AI 执行安全测试的行为边界

1. **只在测试环境执行**。禁止对生产环境执行任何主动测试（探测除外：仅可访问公开页面确认环境信息，不发送攻击载荷）；
2. **不植入、不留后门**：测试产生的临时数据（测试账号、上传文件）测试完清理，清理方式记录在 T10 中；
3. **不利用、不扩散**：发现的漏洞信息只写入 T10 报告和与用户的对话，不用于其他用途；
4. **payload 是测试手段**：使用的测试载荷全部记录在 T10 中，保证可复现、可审计；
5. 无法完成的检查项（如需要真实环境、专业工具）→ 在 T10 中标注"未覆盖+原因"，不假装测过。
6. **测试环境缺失降级**：若项目无独立 test 环境（dev=test 一体或压根无 test），安全测试在 dev 环境执行并明确标注「非独立测试环境」；**严禁对 prod 发送任何攻击载荷**（仅可访问公开页面确认环境信息，不投送 payload）。若 dev 即生产（无隔离环境），则只做静态分析 / 配置审查 / 代码审计，在 T10 标注「未做动态渗透（无隔离测试环境）」及原因，不假装测过。
