# AI 开发规范文档套件（ai-dev-guide）

一套让 AI 受控开发的规范体系：先调研出文档、再按文档开发、修改走变更控制，杜绝随意开发。

## 快速使用

把本目录放进项目（或复制模板到项目文档目录），对 AI 说：

> **第一步让 AI 加载本规范（读项目内 `ai-dev-guide-lite/00-总则.md`）。规范一旦加载，我之后说的任何话 AI 都按规范处理——调研读 part1、开发读 part2、改既有东西读 30-变更控制、接手既有项目先走 part1/12，不用每句重复提规范。**

（规范可封装成 Skill 来加载，但**使用时以本规范正文为准**；Skill 只是加载手段，不是事实源。）

总则是整个体系的唯一入口——**无论是调研还是开发，AI 接到任何任务的第一步都是加载规范（即读 00-总则）**。总则开头的「快速路由」会告诉它当前任务该跳到哪份规范：

- 接新需求 / 需求不清 → 读 part1 调研规范，产出 T1 需求文档 + T2 功能清单
- 接手既有项目（文档不全）→ 读 part1/12，盘点现状 + 反向补建 T2 功能清单和 T8 功能说明
- 新功能开发 → 读 part2 开发规范，先出 T3/T4/T5 设计文档再写码，完成时产出 T8 功能说明
- 改功能 / 小修改 → 读 30-变更控制规范，先评估再动手
- 功能测试通过 → 读 part2/26 安全测试规范，产出 T10 安全测试报告，漏洞分级处置
- 上线 → 读 25-上线方案规范（上线准入含 T10 结论：无未处置严重/高危漏洞）
- 首次部署 / 环境搭建 / 架构变更 → 读 part2/27 部署管理规范，产出/更新 T11 部署文档

## 参考话术（对 AI 怎么说）

把下面任意一句直接发给 AI 即可触发本规范。按需复制，括号里的是可选替换项。

**① 通用开头（推荐默认开场 · AI 会先问意图）**
> 第一步让 AI 加载本规范（读项目内 `ai-dev-guide-lite/00-总则.md`）。规范加载后，AI 先问："这次任务是**完善规范**、**使用规范**、还是**两者都**？"——我回答后它再按对应路线走（完善→31，使用→part1/part2/30，两者都→先完善再以新规范开发）。不用每句重复提规范。

> 若我已明确就是要改规范、不想被反问，可直接用 ⑧ 跳过询问、直接进入 31 流程。

**② 新项目 / 新需求（从零开发）**
> 这是个新项目（【项目名】）。先按 part1 调研规范做需求调研，产出 T1 需求文档和 T2 功能清单，需求冻结后按 part2 出设计文档再开发，每功能收尾产出 T8 功能说明。

**③ 接手既有项目（文档不全 —— 已有代码，没文档）**
> 这是接手项目，已有代码但文档不全。先按 `12-接手既有项目规范` 盘点现状、反向补建 T9 功能树 / T2 功能清单 / T8 功能说明和 `docs/项目记忆.md`，登记《接手冲突核对与解决记录》，文档基线就绪后再进入正常开发。

**④ 改功能 / 小修改（防乱改）**
> 我要改【功能编号/名称】。先按 `30-变更控制规范` 读它的 T8 现状、做影响评估，改完同步更新 T8、功能树、开发计划表和 CHANGELOG，再告诉我完成。

**⑤ 功能测试 + 安全测试（上线前门禁）**
> 功能开发完了，先按 `24-测试与验收规范` 跑 T6 回溯验收，再按 `26-安全测试规范` 做 T10 渗透测试、按漏洞等级处置并复测，无未处置严重/高危漏洞再走上线。

**⑥ 上线 / 部署**
> 准备上线【版本/功能】。先按 `25-上线方案规范` 出 T7（含回滚方案，无回滚不上线），并确认 T10 结论已闭环；部署按 `27-部署管理规范` 的 T11 文档执行，部署后回写 T11 与 CHANGELOG。

**⑦ 把最新规范同步到本项目**
> 把 `ai-dev-guide/` 主本整目录覆盖到本项目的 `ai-dev-guide/`（或跑 `update_project_guide.py <本项目目录>`），覆盖后重读 `00-总则.md` 生效。

**⑧ 更新 / 修订规范本身（仅完整部署 · 规范维护者）**
> 这条规范要加一条新规则（【具体说明，如"新增：AI 改模型+写迁移后必须先应用迁移再启动"】）。先按 `part3/31-规范演进与维护规范` 登记 → 提修订方案和影响面 → 我确认后你改文档、升版本号、写 `part3/CHANGELOG-规范套件.md`、并同步 Skill 副本和已用项目的副本，改完告诉我。

> 说明：本项目若只部署了精简版（无 part3），AI 无权自改规范——应把缺口/修订建议反馈给你，由规范维护者（主本）统一迭代。

> **提示**：规范本身不强制 git；无 git 时变更回退锚点用 `30-变更控制规范` 的「`.backup/` 快照」方案兜底。接手项目若不先补文档基线，AI 不应硬读尚不存在的 `docs/` 文档（见总则「〇-1」前置路由）。

## 两种部署形态

套件既可完整交付，也可精简交付——两者都能正常约束 AI 开发：

| 形态 | 包含 | 适用 | 生成命令 |
|------|------|------|---------|
| 完整部署 | 00-总则 + part1 + part2 + 30 + part3 | 规范维护者自用、需体系自我迭代 | `init_project_docs.py <项目> --name X --with-guide` |
| 精简部署 | 00-总则 + part1 + part2 + 30（**不含 part3**） | 交付项目、只给"需求+开发"内容 | `init_project_docs.py <项目> --name X --with-guide --lite` |

- **必读四块**（00-总则、part1、part2、30）齐全即可工作；
- **part3 是可选模块**：只关乎"规范自身怎么迭代"，缺了只是失去自我修订能力，**不影响开发管控与防乱改**；
- 精简部署下若 AI 发现规范缺口，按《00-总则》「〇-3 缺失降级」直接反馈用户、不擅自改规范。

## 两阶段工作流

```
【阶段一：调研】                          【阶段二：开发】
用户提需求 → AI 按规范提问澄清            按任务类型路由：
  → 产出 T1 需求文档 + T2 功能清单          新功能：读 T1/T2 → T3/T4/T5 → 代码 → T8 → 测试（T6）
  → 用户确认 → 需求冻结                     改功能：读 30 + T8 现状 → 影响评估 → 先改文档再改代码
                                            小修改：直接做 + 记 CHANGELOG
                                          【安全门】功能测试通过 → 安全测试（T10）→ 漏洞处置+复测
                                          【上线门】T6+T10 均通过 → T7 上线方案 → 按 T11 部署文档执行
                                          【部署】每次部署后回写 T11 部署记录 + CHANGELOG
```

## 防乱改四道闸

1. **功能树定位**：改前必须在 T9 功能树定位目标节点、查依赖关系，树上未涉及的分支一律不动；
2. **影响评估**：改前必须输出涉及功能/文档/库表/接口的影响面；
2. **范围锁定**：修改文件清单经确认后即为边界，越界必须停下；
3. **文档同步**：改代码必同步更新 T8 功能说明 + T9 功能树（未更新 = 未完成）+ CHANGELOG。

## 设计理论与依据

本规范不是凭空设计，而是踩在四条成熟工程理论上，并用 AI 时代的 Context Engineering 做了重述。理解这些理论，便于你和团队判断"为什么这样约束 AI"，也便于对外推介时给出处。

| 理论 | 核心信条 | 在规范中的落地 |
|------|---------|--------------|
| **需求工程（Requirements Engineering）· What/How 二分** | 需求描述"做什么"（What），设计/实现描述"怎么做"（How），两者必须分离，需求不能写死实现 | T1/T2 = What（需求层）；part2/T8 = How（实现层）；需求冻结（《11》）保证开发前 What 已确认 |
| **FODA 特征树（Feature-Oriented Domain Analysis, SEI 1990）** | 用层级特征树表达"系统由哪些功能组成、谁依赖谁"，动手前先定位"这次动的是哪个特征" | T9 功能树（M→F→FP 层级 + 依赖表 + 特征约束 requires/excludes/alternative），是防乱改的边界地图 |
| **SSOT / 活文档（Living Documentation, Martraire；Spec-by-Example, Adzic）** | 文档即唯一事实源，且须与代码同步、可被检测 | `docs/` 为唯一事实源；T8 同步门禁（《30》变更控制）；v1.31 需求活文档原则（T1/T2 正文 = 当前完整需求，修订记录仅作追溯） |
| **Context Engineering（Karpathy 等, 2024）** | 大模型表现取决于喂给它的上下文是否"正确且最小" | 总则路由决定读什么；必读清单「精准加载」（《00》，v1.37）；`docs/` 装着 What/Which/How，是给 AI 的上下文三件套 |

**一句话背书**：本规范 = 需求工程的 What/How 二分 + FODA 特征树定位 + SSOT 活文档，落地为 AI 的 Context Engineering。

**三层认知模型（规范的设计骨架）**：
- **干什么（What）** —— T1 项目需求文档 + T2 功能清单（含 NFR、验收可验证）
- **哪个（Which）** —— T9 功能树（层级 + 依赖 + 特征约束），修改/新增前强制定位节点
- **怎么干（How）** —— part2 设计文档 + T8 功能说明（功能级唯一事实源）

> part3（规范演进）是"元层"——只管规范自己怎么迭代，不进这三层。

## 首次接入项目时

1. 在**项目根目录**下创建 `docs/` 并建子目录（requirements / tech / test / release / deploy / features）——所有实际文档都往这里放；
2. 把技术栈信息填入各规范中的【填空位】（命名规范、响应结构、测试目录等）；
3. 已有功能的项目：可让 AI 按现有代码反向补建 T9 功能树、T2 功能清单和 T8 功能说明文档，逐步补齐台账；
4. 建议在项目的 AI 规则文件（如 CLAUDE.md / .cursorrules）中加一句：`开发任何任务前，先读 ai-dev-guide-lite/00-总则.md 并遵照执行`。
