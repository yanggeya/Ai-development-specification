## 二、编码纪律

### 1. 严格按文档实现
- 只实现 T1/T3/T4/T5 确认的内容。**文档没写的行为 = 不做**；
- 实现中发现文档遗漏、矛盾或不可行 → **停下提问**，说明问题与建议，等确认后更新文档再继续；
- 禁止「我觉得这里应该加个 XX」式的自我发挥；好想法可以提出，由用户决定是否纳入。

### 2. 代码结构
- 遵循项目已有目录结构与编码风格（【项目规范填空位：______】）；
- 新功能按模块组织，与 T3 模块拆解对应，让代码结构可从文档反查；
- 公共代码复用已有工具/组件，不重复造轮子。

### 3. 变更边界
- 每次开发的改动范围 = 文档评估确认的范围；
- 看到无关代码问题 → 记录并单独报告，不顺手修；
- 禁止引入文档未确认的新依赖。

### 4. 注释与可追溯
- 关键业务逻辑注释注明对应的功能编号（如 `# F003: 资产状态流转规则`），便于文档↔代码互相追溯。

### 5. 编码安全纪律（安全左移落到写码）

> 安全不是写完再测，而是写码时就守住。下列任一条违反即触发对应红线（R10–R17）。

- **输入校验内建**：外部输入（请求参数、文件、header、第三方回调）在入口处即校验类型/边界/白名单，不信任任何上游；校验契约以《22》T5 为准。
- **输出编码**：拼 HTML/日志/SQL 前做对应转义；禁止把用户输入直接拼接进查询或命令（红线 R11）。
- **密钥与凭证**：禁止硬编码（红线 R10）；密钥走环境变量/密钥管理，提交前 secret scanning。
- **认证/授权不后补**：鉴权判断按《22》设计就位，不在"能跑通"阶段省略；越权风险（横向/纵向）在编码时即处理。
- **日志不泄密**：日志不记明文密码、token、证件号；报错不向调用方回显堆栈/SQL/路径（呼应《22》错误结构）。
- **权限与访问控制纪律（对齐安全工程原则）**：① **最小权限**——进程/服务/代码只申请完成功能所需最小访问（文件/网络/DB）；② **默认拒绝**——任何访问入口缺省拒绝，显式授权才放行；③ **失败安全（fail secure）**——鉴权/策略判定失败时拒绝而非放行，异常/超时降级到安全态；④ **职责分离（SoD）**——审批与执行、发起与部署分由不同主体，代码不把"自己审自己"当合法路径；⑤ **完全仲裁**——每次请求鉴权，授权结果不长期缓存绕过（呼应《22》鉴权设计）。

- **前端安全纪律（含网站/后台前端，最高频漏洞区）**：① **XSS 防护**——渲染用户输入/富文本须经安全消毒（如 DOMPurify），模板默认转义，禁止 `v-html`/`dangerouslySetInnerHTML` 直接插入未净化内容；② **token 存储分级**——鉴权 token 优先存 httpOnly Cookie（防 XSS 窃取）；若用 localStorage 须配 CSRF 防护并明示风险；③ **CSRF 防护**——cookie 鉴权接口须带同源 CSRF token 校验（SameSite=Strict/Lax + token 双提交）；④ **前端密钥分级**——地图/统计等 SDK 的「公开 key」可放前端，但后端密钥/数据库口令绝不可进前端代码或前端可访问配置，环境靠构建期注入；⑤ **敏感字段不出前端**——接口不应向前端返回其无权限查看的字段（后端按角色裁剪）。

### 5.1 依赖安全
- 新增/修改依赖须经存在性校验（确认包真实存在、维护者可信、发布时间合理），禁止引入 AI 凭语料臆造的不存在包名（包幻觉，红线 R12）；
- 依赖必须锁定 lockfile 并校验 hash（如 pip `lock`、npm `package-lock` + `--frozen-lockfile`）；禁止提交未锁定的新依赖；
- 依赖版本须落在当前安全版/白名单；`pip-audit` / `npm audit` 等作为强制 CI 门禁，已知 CVE 直接阻断合并；
- CI 扫描安装脚本（postinstall）与依赖来源，杜绝供应链投毒。

### 5.2 框架与组件默认配置隐患防护

> 许多漏洞不是代码写的，而是**框架/中间件用默认配置直接上线**带来的。引入任何框架、库、中间件、云平台服务时，必须先查其默认配置的安全隐患并**显式加固**，禁止"开箱即用就上线"。

- **引入前必查默认风险**：选型/接入时先列出该框架/组件已知的"默认不安全项"，至少覆盖：调试模式（如 `DEBUG=true`/`debug=True`）、默认密钥/签名密钥（如 `SECRET_KEY`/`secret_key_base` 缺省或弱值）、暴露的管理/监控端点（如 Actuator、phpMyAdmin、Django admin 未鉴权）、宽松 CORS（`*`）、默认开放权限（对象存储公开 ACL、K8s 默认 ServiceAccount 挂载 token）、示例/欢迎页与默认账号；
- **显式加固、不留默认**：上述每项默认值必须显式改为安全值，并在 T3/T8 或配置注释中记录"默认值 → 安全值"的改动，便于复核；
- **禁止默认上线**：未做加固清单确认的功能不得进入测试/上线流程（与《20》安全需求第⑤项闭环）；
- **项目级速查表（填空位）**：项目在 `【框架默认风险速查表：______】` 维护所用框架的默认隐患与加固项（模板见下方），新引入框架时补充，禁止凭记忆。

**框架默认风险速查表（模板，项目按实际技术栈补充）**

| 框架/组件 | 默认隐患 | 安全加固（必做） | 责任人/位置 |
|----------|---------|----------------|-----------|
| 【如 Django】 | DEBUG=true 暴露堆栈；SECRET_KEY 弱 | 生产 DEBUG=false；SECRET_KEY 走环境变量 | T3 / settings |
| 【如 Spring Boot】 | Actuator 端点未鉴权暴露 | 关闭/加鉴权敏感端点 | 配置 |
| 【如对象存储】 | ACL 默认公开 | 默认私有，按需最小授权 | T11 |
| 【如 Express】 | 无安全响应头、CORS 默认不限制 | 启用 helmet、显式 CORS 白名单 | 中间件 |
| 【……按项目补充】 | | | |

### 6. 架构纪律
- **复用优先于重写**：改动前先检索代码库与内部私有包，已有实现一律复用，不重复造轮子；看不到的实现先问，不擅自重写；
- **强制分层**：路由/UI 不含业务与数据逻辑，领域逻辑在 service/domain 层；为"最快修 bug"把修复放症状处视为违规；
- **前端强制分层**：页面/路由只负责渲染与导航，业务与状态在 store/服务层，所有后端调用经统一 API 封装层（baseURL/拦截/错误处理）；禁止在单文件组件内直写请求逻辑与业务判断（呼应本规范 §5 前端安全、呼应《20》前后端分离专项）；**前端的组件划分/状态管理/样式约定/可访问性/构建产物等专项要求见《28-前端开发规范》**——涉及前端代码时 28 与本规范同读，本条只定分层底线；
- **禁止跨层隐式共享可变状态**：全局变量、单例缓存、共享文件句柄须登记归属，改动须评估下游订阅者；事件发布须登记订阅者契约；
- **尺寸上限**：单文件/单函数不超过约定上限（如 200–500 行 / 单函数 80 行），超出须拆分；单一职责；
- **魔法数字命名**：硬编码数值抽为命名常量并注释业务含义（如超时、重试、限额）；
- **中心化类型来源**：类型定义集中管理（如 `@types/index.ts`），模块用 Pick/Omit 派生，不就地新建重复类型；
- **遵守项目生态**：只使用项目声明的语言/框架/版本，跨语言命名与包约定不混用；优先当前稳定 API，不用已废弃写法（CI 跑 deprecation 检查）；
- **并发安全**：涉及共享资源（临时目录、文件、缓存、DB）的代码默认并发安全，须被告知预期并发量并有对应测试；
- **禁止全局重写**：既有业务不变量（历史边缘情况、定价/权限规则）不得为"清理"重写覆盖，须以测试/文档显式锁定；
- **人工理解**：关键代码（如鉴权、支付、数据迁移）须人工通读理解，AI 须能解释而非单纯重写；超长函数须拆分后再改。

### 7. 性能纪律

> 性能方案（分页/分批/异步/缓存/索引/分区）须在 T3/T4/T5 设计阶段确定并写进文档，编码阶段只实现已确认方案，不在写码时才临时决定架构级性能手段（呼应《20》性能设计项）。

- **避免 N+1 查询**：用批量/关联查询或预加载替代循环单查；列表与导出须评估数据量级，超限须分页或异步；
- **资源显式释放**：文件句柄、连接、游标、临时目录用毕必须关闭/清理，杜绝内存泄漏；
- **大批量异步/分批**：大批量写、导入、通知走分批或异步，禁止单次同步阻塞主流程；耗时操作标注预期量级并有边界验证。

### 8. 异常处理
- **禁止空 catch / 吞异常**：捕获异常必须记录日志并处理或向上抛，不得 `except: pass` / 空 `catch`；
- **统一异常出口**：错误信息不向调用方泄露内部细节（堆栈/SQL/路径），由统一层转换为安全错误码（呼应《22》错误码表）；
- **关键路径可观测**：失败必须记日志，便于事后定位，禁止静默失败。

## 三、完成时义务（三个必做）

1. **自测**：按 T5 接口文档逐个验证接口行为，按 T1 验收标准逐条过；
2. **产出功能说明文档**：按 `templates/T8-功能说明文档模板.md` 生成 `docs/features/F-<编号>-<功能名>.md`——这是强制产物，没有它任务不算完成；
3. **报告**：完成报告需包含——实现了哪些功能点、对应文档、自测结果、遗留问题；
4. **流转下一环节**（提醒用户，不要停在"代码写完了"）：
   - 功能测试 → 读《24-测试与验收规范》，产出 T6；
   - 安全测试 → 读《26-安全测试规范》，产出 T10，无未处置严重/高危漏洞；
   - 发布准备 → 读《25-上线方案规范》产出 T7，环境信息/部署手册以《27-部署管理规范》的 T11 部署文档为准。
