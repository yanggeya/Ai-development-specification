# 20-开发技术需求规范 —— 从业务需求到技术方案

> **本文件规定新功能进入开发前，如何把 T1/T2 中的业务需求转化为技术需求文档（T3）。P1 级任务必须产出完整 T3 并经确认；P2 级可产出简版（结构相同，篇幅从简）。**

- 版本：v1.12
- 前置阅读：`00-总则.md`、T1、T2

---

## 一、阶段准入条件（开工前检查）

- [ ] 对应功能点已登记在 T2 功能清单中，需求已冻结（T1 状态为「已确认」）；
- [ ] 功能涉及的业务规则、边界条件在 T1 中有明确结论；
- [ ] 开放问题中与本次开发相关项已全部决策。

任一不满足 → 回到《10-需求调研规范》补问，不得带疑开工。

## 二、T3 技术需求文档要求

保存至：`docs/tech/T3-<模块名>.md`，须包含：

1. **模块拆解**：本次功能拆成哪些技术模块/服务，各自职责边界；
2. **技术选型**：框架、关键依赖库及版本（技术栈填空位：`【本项目使用：______】`），选型理由一句话；
3. **数据流说明**：数据从哪来 → 怎么处理 → 存哪里 → 怎么展示，一条链路说清；
4. **技术规则**：T1 中业务规则的技术化表达（如校验规则、状态机、计算公式）；
5. **技术风险**：性能瓶颈点、外部依赖风险、需要预研的技术点；
6. **对既有系统的影响**：是否复用/修改已有模块、是否影响已有功能；
7. **安全需求（设计阶段即明确，对齐 SDL）**：把安全作为需求项而非上线前补丁，设计阶段须覆盖——
   ① **认证/授权与权限模型**：认证方式（免登/登录/角色）；权限模型以**三权分立（等保三员）**为核心——系统管理员 / 安全管理员 / 审计管理员三角色相互独立、互不兼任（即用户所称"三权限"），任何角色不得越权代行他者职责；业务权限遵循 RBAC 且支持数据/字段级最小授权；**职责分离（SoD）**：审批与执行、发起与部署不得由同一主体完成；
   ② **威胁建模（STRIDE）**：对涉及认证、支付、数据变更的关键链路，画数据流图识别威胁（Spoofing 伪造 / Tampering 篡改 / Repudiation 抵赖 / Information Disclosure 信息泄露 / DoS 拒绝服务 / Elevation of Privilege 提权），高风险项在设计阶段即定缓解方案；
   ③ **敏感数据范围与保护**：按分类分级（公开/内部/机密/受限）确定保护方式（加密、脱敏、不出域），并做隐私设计（数据最小化收集、默认不留存）；
   ④ **审计与可追溯**：操作必须留痕，关键表加 `created_by`/`updated_by`；审计日志独立存储、不可篡改、留存 ≥ 6 个月；
   ⑤ **输入边界与校验规则**；
   ⑥ **框架/组件默认配置隐患评估**：选型时先列出候选框架/中间件的默认不安全配置（调试开关、默认密钥、暴露的管理端点、宽松 CORS、默认开放权限等），给出显式加固方案，**禁止"用默认配置直接上线"**（落实见《23-编码实现规范》框架默认配置加固条款）；
   ⑦ **加密与密钥标准**：明确算法标准（密码用 bcrypt/argon2 慢哈希；传输用 TLS；静态加密算法约定），密钥统一走环境变量/密钥管理，禁止自创加密。
8. **性能设计（设计阶段前置，避免"写完才发现慢"）**：在数据量级与并发预期明确前不锁定方案——① **量级预估**：预估每张核心表的行数量级（千/万/十万/百万+）与峰值读写 QPS；② **列表/导出/统计类**：预估结果集量级，决定是否同步分页（限定每页上限）还是异步任务（超限必须异步，禁止一次返回全量）；③ **缓存/聚合**：高频读、重聚合走缓存或物化，避免每次实时计算；④ **大表策略**：超量级表在设计时定索引、分区或归档策略；性能方案须写进 T4/T5，编码只实现不重新决策。

9. **前后端分离专项（含网站/后台管理前端项目必做）**：若项目含前端（尤其前后端分离、独立 `/admin` 后台），设计阶段须落实——
   ① **接口契约先冻结**：T5 接口设计必须在前后端编码前完成并确认，作为双方契约；前端按契约本地 mock/桩并行开发，不阻塞等后端实现；
   ② **前端工程结构**：在 T3 明确前端目录约定（页面 / 组件 / store 状态管理 / api 调用封装层分离）、状态管理方案（如 Pinia/Vuex/Redux）、接口请求统一封装（baseURL/拦截器/错误处理），禁止把请求与业务逻辑写进单文件组件；
   ③ **前端数据流与缓存**：前端状态如何与后端响应同步、列表/详情数据是否本地缓存及失效策略，设计阶段即定；
   ④ **部署形态对齐**：前端构建产物 / 后端服务 / 反向代理的部署拓扑（同域 `/admin` 子路径或子域）在 T3 即与《27》T11 对齐，决定 Cookie 域、CORS 来源与反代配置。

## 三、准出检查（提交用户确认前）

- [ ] T1 中每个验收标准都能对应到 T3 的某个技术模块？
- [ ] 技术选型与项目既有栈一致（或说明了理由）？
- [ ] 没有引入未经确认的新依赖？
- [ ] 风险点都有应对方案或明确的接受声明？
- [ ] 核心表量级与并发已预估，列表/导出/统计接口已定同步分页 or 异步方案（写进 T4/T5）？
- [ ] 前后端分离项目：T5 接口契约已先于编码冻结、前端工程结构/状态管理/api 封装已在 T3 明确（见第 9 项）？

```markdown
## 1. 模块拆解
<模块名、职责、边界，一张图或列表>

## 2. 技术选型
<框架/依赖/版本及理由>

## 3. 数据流
<来源 → 处理 → 存储 → 展示>

## 4. 技术规则
<校验/状态流转/计算规则，与 T1 业务规则一一对应>

## 5. 风险与影响
<技术风险、对既有功能的影响>

## 6. 安全需求
<认证/授权方式与权限模型（三权分立+最小授权+职责分离）；STRIDE 威胁建模结论；敏感数据分类分级与保护（加密/脱敏/不出域）+ 隐私设计；审计留痕与独立审计日志（不可篡改、留存≥6月）；输入边界；框架/组件默认配置隐患与加固方案；加密与密钥标准>

## 7. 性能设计
<核心表量级预估（行数/QPS）；列表/导出/统计接口：同步分页 or 异步任务及量级阈值；缓存/聚合策略；大表索引/分区/归档策略>

## 8. 前后端分离设计（如适用）
<接口契约冻结方式（T5 先于编码）；前端目录/状态管理/api 封装方案；前端数据流与缓存策略；部署拓扑（同域/admin 子路径 or 子域）与 T11 对齐>
```

确认后进入数据库设计（21）与接口设计（22）。
