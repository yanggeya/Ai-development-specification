## 二、组件纪律

### 1. 组件划分
- **单一职责**：一个组件只做一件事（展示 OR 容器 OR 交互），业务组件与展示组件分层；
- **按业务领域拆，不按页面类型堆**：`UserCard`、`OrderList` 而非 `PageAFoo`、`PageBBar`；
- **目录分层**：公共/共享组件进共享目录，业务组件就近所属业务域；跨业务域直引视为违规（见 §2.4 复用边界）；
- **与 T3 模块拆解对应**：组件层级可从文档反查，新增/拆分组件需在 T3/T8 同步登记。

### 2. 命名约定
- 组件名 PascalCase、文件名与组件名一致；props 用驼峰，事件名 `onXxx` 或 `on-xxx`（按项目【填空位】）；
- 业务语义命名优先于技术形态命名（`OrderStatusBadge` 优于 `RedBadge`）；
- 布尔 prop 用 `is/has/can` 前缀（`isVisible`、`hasPermission`）；
- 禁止 `data1/data2/temp/xxx2` 这类无义命名。

### 3. props / emit 契约
- **类型化**：所有 props 必须声明类型（TS 接口或运行时校验），禁止 `props: any`；
- **必填/默认值显式**：必填标 `required`，可选给默认值；默认值须为基本类型或工厂函数（避免引用类型共享）；
- **禁止透传整个对象当 props**：父组件传业务对象时应拆为最小必要字段，或显式声明 `entity` prop 并在 T8 注明契约；
- **事件契约**：emit 须声明事件名与载荷类型；子组件不直接调用父组件方法（除声明的事件外）；
- **组件不直接调 API**：API 调用经统一封装层（baseURL/拦截/错误处理），组件只消费 store/服务层返回的数据（呼应 23 §6 前端强制分层）；
- **副作用边界**：组件内副作用（订阅/定时器/全局事件）必须在卸载时清理。

### 4. 复用边界
- 公共组件进 `共享目录`（项目【填空位】），跨业务域可用；业务组件只在其业务域内用；
- 改公共组件前先查下游调用方（grep 调用点），评估影响面，按《30-变更控制规范》走；
- 三处以上重复代码 → 抽公共组件或工具函数；少于三处不预先抽象（避免过度设计）。

### 5. 尺寸上限
- 单组件文件不超过 300 行（含模板/脚本/样式）；超出须按"展示/容器/逻辑"拆分；
- 单函数不超过 50 行（前端逻辑函数比后端更应短小）；
- props 数量超过 7 个 → 信号：组件职责过载，考虑拆分。

### 6. 权限相关组件（按钮 / 菜单显隐）
- **权限不前端写死**：按钮 / 菜单的显隐与可用状态，由登录后后端下发的「角色 / 权限集」驱动，禁止前端写死「某角色能用某功能」假设（呼应《22-接口设计规范》前后端权限源同源，v1.24）；
- 角色 × 接口权限矩阵为单一真相源；admin / 超级管理员为矩阵全局例外，前端对其直接视为全权限（不重复 22 的 admin 例外细则，仅引用）；
- 权限集缺失或待确认 → 按【待确认】处理、问用户，不臆测前端该显隐什么。

## 三、状态管理分层

### 1. 三层划分
- **组件本地状态**：仅组件内部用、不影响其他组件（如输入框聚焦、展开收起）；
- **业务领域 store**：跨组件共享的业务数据（如当前用户、订单列表、购物车），按业务域模块化；
- **全局 app state**：应用级配置（主题、语言、特性开关），独立于业务 store。

### 2. 分层纪律
- 组件内不直写业务逻辑与请求逻辑（呼应 23 §6 前端强制分层）；
- store 不直接操作 DOM、不持有 UI 状态（loading 可在 store，但 visible/disabled 留组件本地）；
- 跨 store 调用须显式声明依赖，禁止 store 之间隐式循环依赖；
- 后端调用一律经统一 API 封装层（baseURL/拦截/错误处理/鉴权头），store 调 API 层、组件订阅 store。

### 3. 持久化与 hydration
- 持久化（localStorage/sessionStorage/IndexedDB）须显式声明 key 命名空间，避免全局污染；
- 从存储恢复状态须做 schema 校验（旧版本数据可能不兼容），失败时回退默认值；
- 服务端渲染（SSR）项目须区分服务端与客户端状态，避免 hydration mismatch。

## 四、样式约定

### 1. 作用域隔离
- 样式必须作用域隔离：scoped CSS / CSS Modules / CSS-in-JS / Tailwind utility（按项目【填空位】）；
- 禁止全局样式污染（`*{}`、`body{}` 改动须评估全局影响，按《30》走）；
- 公共样式 token 进主题文件，业务样式就近组件。

### 2. 设计令牌（design tokens）
- 颜色、间距、圆角、字号、阴影、z-index 等抽为命名 token，禁止内联魔法值（`color: #3b82f6`、`margin: 13px`）；
- token 集中管理（如 `theme/tokens.css` / `tailwind.config.js`），改动 token 走《30》评估全量影响；
- 暗色/浅色主题用 token 切换，不在组件里硬编码颜色分支。

### 3. 响应式与适配
- 断点用 token 定义（`sm/md/lg/xl`），不散落硬编码；
- 移动优先或桌面优先由项目【填空位】定，但一旦确定全项目一致；
- 禁止 `!important` 解套娃式覆盖，遇样式冲突先理清层级，不靠权重堆叠。

## 五、可访问性（a11y）基线

> 前端是给人用的，可访问性不是可选项。下列为最低基线，违反即视为缺陷。

- **语义化标签**：用 `<button>`/`<nav>`/`<main>`/`<dialog>` 等语义标签，不滥用 `<div onClick>` 当按钮；
- **键盘可达**：所有交互元素必须键盘可操作（Tab/Enter/Esc），焦点顺序符合视觉顺序；
- **焦点管理**：弹窗/抽屉打开时焦点进入、关闭时焦点还回触发元素；`tabindex` 不滥用（仅在自定义组件必要时用）；
- **ARIA 最小集**：仅语义标签无法表达时用 ARIA（`aria-label`/`aria-expanded`/`aria-hidden`），不冗余标注（如 `<button aria-role="button">` 是错的）；
- **对比度**：文本与背景对比度至少 4.5:1（WCAG AA），可用工具校验；
- **不依赖颜色单独传达信息**：错误状态除红色外应有图标/文字（色弱用户友好）。

## 六、构建与产物

### 1. 构建产物校验
- 构建脚本须有产物校验：文件大小异常、Source Map 缺失（生产该有或显式关闭）、资源 404 须报警；
- 资源指纹（hash 文件名）必须开启，确保缓存策略可靠；
- 按需加载（路由懒加载 / 动态 import）用于大组件与低优先级页面，首屏不加载非首屏代码。

### 2. 环境变量注入
- 前端可访问的环境变量须经构建期白名单注入（如 `VITE_*` / `NEXT_PUBLIC_*`），未白名单的变量不暴露到产物；
- **后端密钥/数据库口令绝不可进前端代码或前端可访问配置**（呼应 23 §5 前端密钥分级）；
- 不同环境（dev/staging/prod）的变量须显式区分，构建时按环境注入，禁止运行时硬编码切换。

### 3. Source Map 策略
- 生产环境 Source Map 不对公网开放（可上传到错误监控平台，或仅内网可访问）；
- 上线前确认 Source Map 不会泄露源码（如上传 Sentry 后删除产物侧 map）。

## 七、前端测试纪律

> 与《24-测试与验收规范》衔接：前端测试是 T6 的一部分，本节只列前端专项要求。

- **组件单测**：公共组件须有单测，覆盖 props 各分支与关键交互（点击/输入/焦点）；
- **业务组件关键路径测试**：表单提交校验、列表筛选、弹窗开关等关键交互须有测试；
- **快照测试（可选）**：UI 稳定的展示组件可用快照测试，但快照失败须人工核实，不盲目更新；
- **不测实现细节**：测行为（点击后发生什么），不测内部状态私有字段；
- **E2E 视情况**：核心用户流程（登录/下单/支付）建议 E2E，但 E2E 维护成本高，按项目需要定。
