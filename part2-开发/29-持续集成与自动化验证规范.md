# 29-持续集成与自动化验证规范

> **本文件规定"对自动化验证有强要求、需要深度集成 CI/CD 管线"的项目如何编排质量门禁。可选模块：仅当 `docs/tech/技术栈约定.md` 的「§8 CI/CD 与自动化验证」声明启用时适用；未启用或轻量项目走《24》最小门禁即可，不强制本规范。**

- 版本：v1.0
- 前置阅读：`00-总则.md`、`24-测试与验收规范.md`、`26-安全测试规范.md`、`docs/tech/技术栈约定.md`
- 产出文档：CI/CD 管线配置（项目源码，非 `docs/`）+ 门禁结果留痕（按 §8 约定）

---

## 一、启用判定（是否走本规范）

- 项目 `docs/tech/技术栈约定.md` §8 填写了启用档位 → 本规范生效；
- 未填写 / 选"轻量" → 仅按《24》最小门禁（build+test 卡住、门禁配置锁定），不要求多阶段管线与合并/发布闸门；
- 触发"强验证"的典型信号（满足任一即应考虑启用）：① 多人协作 + 主干保护需求；② 等保/合规要求自动化留痕；③ 发布频率高、需发布闸门防误发；④ 用户明确要求"无通过禁止合并"。

> 一句话：**本规范是《24》最小门禁的"企业加强版"，按项目需要启用，小型项目不背包袱。**

## 二、管线分层（多阶段，任一阶段失败即阻断）

标准管线阶段顺序（项目可在 §8 声明裁剪/增项）：

1. **构建（build）**：编译/打包；产物须带指纹（commit/timestamp），可溯源；
2. **单元/集成测试（test）**：运行《24》T6 用例，全绿方可继续；
3. **静态扫描（scan）**：SAST + 依赖漏洞扫描（`pip-audit`/`npm audit`，呼应《23》依赖审计、R12 幻觉包拦截）+ 密钥/秘文扫描（R10）；已知高危/密钥泄露直接阻断；
4. **质量门禁（quality gate）**：覆盖率下限、复杂度上限等——阈值由人类在配置锁定（呼应《24》门禁配置锁定、R17 禁止自降）；
5. **安全门禁（security gate）**：内置《26》自动化手段（SAST/DAST/模糊测试/配置校验/组件治理），作为管线关卡而非仅人工；
6. **产物归档（artifact）**：通过前述关卡后归档可部署产物，关联构建号；
7. **发布/部署门禁（release gate）**：仅从受保护分支/tag 触发；部署后回写 `docs/deploy/T11-部署文档.md`（环境信息以 T11 为准，呼应《27》）。

## 三、合并门禁（强验证核心）

- 目标分支（main/release）开启**分支保护**：禁止直接 push、禁止 bypass；
- PR/MR 合并前须全部 required checks 绿（含上述各阶段）；
- **AI 禁止**：自降阈值、跳检查、加 bypass/特殊 tag 绕过（触犯 R17，同《24》门禁锁定）；合并门禁配置与代码同源受控，改动走《30》。

## 四、策略门禁（企业强验证项）

- **覆盖率下限**：项目在 §8 声明具体值，未声明不强制具体数、但须有下限且锁定；
- **依赖零高危**：已知 CVE 阻断合并（《23》）；
- **密钥/秘文零泄露**：secret scanning 阻断；
- **必要评审**：合并前由非作者审查（职责分离，呼应《26》SoD）；轻量可由 AI+人工替代两人。

## 五、发布 / 部署门禁

- 仅受保护分支或经审核的 tag 允许发布；
- 发布产物可溯源（commit + 构建号 + 责任人）；
- 部署后回写 T11，发布记录留痕（呼应《25》《27》）。

## 六、配置即项目改动（变更管控）

- CI 配置（yaml/脚本/门禁阈值）属项目源码改动，须走《30-变更控制规范》P3 简化流程（说明 + 基线锚点 + CHANGELOG），禁止无记录进仓库（呼应《24》F11）；
- 门禁阈值调整须显式说明理由并留痕，不得静默改。

## 七、审计与溯源

- 每次门禁结果（通过/阻断/处置）须可回溯到提交、构建号与责任人；
- 阻断须有处置记录（修复/豁免须经显式确认，豁免不得默认）；
- 留痕方式由项目在 §8 约定（CI 平台记录 / `docs/` 留痕均可）。

## 八、与现有规范的关系（SSOT，不重复）

- 《24》测试纪律/最小门禁 = 本规范轻量档；本规范只加"深度管线编排 + 合并/发布闸门"，不重述测试纪律；
- 《26》安全验证手段 = 本规范安全门禁（阶段 5）的内置内容，本规范只规定"如何作为管线关卡"，不重复验证方法；
- 《23》依赖审计 / 《30》变更控制 / 《27》部署文档 = 本规范对应阶段的纪律来源，本规范交叉引用不另行定义。

## 九、自检清单（启用本规范时）

- [ ] `docs/tech/技术栈约定.md` §8 已声明启用档位与阈值？
- [ ] 管线已分层（build→test→scan→quality→security→artifact→release），任一失败即阻断？
- [ ] 目标分支保护开启、PR 合并须 required checks 全绿？
- [ ] 覆盖率/依赖/密钥门禁阈值已锁定（非 AI 自降）？
- [ ] 发布仅从受保护分支/tag，部署后回写 T11？
- [ ] CI 配置改动已走《30》P3 留痕？
- [ ] 门禁阻断有处置/豁免记录（豁免非默认）？
